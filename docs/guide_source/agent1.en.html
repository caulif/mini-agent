Chapter 1

Agent Loop

Run the model–tool loop
Goal Write a loop that requests a model response, executes requested tools, appends their results, and repeats until no tool calls remain.

The problem

  • A single question-and-answer model has no action capabilities - it tells you what to do, but it can't touch your files.
  • Once the model says "I want to call the tool", three new questions arise: Who executes it? How to send the results back? When will it stop?

How it works

Start with a useful simplification: a model request does not execute actions or retain your conversation for you. You provide input and receive output. The client maintains the history and supplies the tools.

So "agent" is not the ability of the model, it is the loop you wrote. The only responsibility of the loop is to translate the "I want to do something" output by the model into real actions, and then translate the results of the actions back into text to feed it. The intelligence is all in the model, and your code is only responsible for transportation and accounting.

What a tool call actually does

A tool call does not execute anything by itself. The model returns a tool_calls array with entries such as {id: "call_01...", function: {name: "read", arguments: "{...}"}}. The arguments field contains JSON encoded as a string. Your program decides whether and how to execute the request.

Understanding this, the whole structure falls into place: The loop is the hands. The model is responsible for thinking, you are responsible for doing it, and you will tell it the results after it is done.

The OpenAI-style conversation format

Before you write a loop, you must first know what a request looks like. The entire protocol actually has only one entry: send a POST to {base_url}/chat/completions. The request body is divided into three parts——

POST {base_url}/chat/completions
{
  "model": "gpt-4o-mini",
  "messages": [ ← entire conversation, a list
    {"role": "system", "content": "You are a coding agent..."},
    {"role": "user", "content": "Help me take a look at config.py"},
    ...
  ],
  "tools": [ ...tool declaration... ] ← The "hands" that the model can use
}

messages is a list, with each entry having the shape {"role": ..., "content": ...}. There are four types of roles in total. Remember their division of labor and use them in every subsequent chapter:

  • system: System prompt to define the identity and rules of the model. Only put it in the first one (Chapter 7).
  • user: What the user said.
  • assistant: What the model says; when it wants to call the tool, this message will have an additional tool_calls array.
  • tool: The result of tool execution, single one, relies on tool_call_id to claim which call it belongs to.

The response is also a JSON. There is only one path that really matters: choices[0].message - This is the model's reply in this turn. In the next turn, you have to stuff it back into messages as it is:

{
  "choices": [
    {
      "message": { "role": "assistant", "content": null,
                   "tool_calls": [ {"id": ..., "function": {"name": ..., "arguments": ...}} ] },
      "finish_reason": "tool_calls" ← Another field on the same level
    }
  ]
}

Note that finish_reason and message are sibling fields at the same level: one contains what the model says, and the other contains the description of "why it stopped." This distinction will come into use shortly.

Where to look up protocol fields

The requests and responses drawn above are not made up by me, they are OpenAI's Chat Completions interface - the entire interface has only this entry: send a POST to {base_url}/chat/completions and return a JSON. To check the exact meaning of any field, look no further than these pages:

  • Definition of each field in the request body (model / messages / tools / max_tokens...): api-reference/chat/create
  • What does the response object look like (choices → message → content / tool_calls, and finish_reason at the same layer): api-reference/chat/object
  • How to coordinate the four roles (system / user / assistant / tool) and complete dialogue examples: api-reference/chat
  • Tool calling this set of conventions (tools declaration, tool_calls return, tool_call_id pairing): guides/function-calling

Compared with the document, you will find that only four fields are used in the request body - model, max_tokens, messages, tools; in the response, only choices[0].message is read (the text is in content, the tool call is in tool_calls), and the other fields are ignored. The protocol is very large, and the agent needs only a small piece - streaming, multi-modal, sampling parameters, logprobs, etc., just pretend they don’t exist for now.

Message pairing requirements

OpenAI style (chat/completions) has mandatory requirements for history structure. This constraint is the source of all the trouble in the following chapters and must be remembered from the beginning:

user "Help me take a look at config.py"
assistant {content: ..., tool_calls: [{id: "call_A", function: {name: read, ...}}]} ← Intent only
tool {tool_call_id: "call_A", content: "..."} ← Must match
assistant "This file defines a CONFIG dictionary..." ← Call it a day

Each tool_call must have a message with the same tool_call_id and the same role as tool, there can be no less or more. This rule will also be used later: in Chapter 4, the pairs must be supplemented when interrupted, and in Chapter 6, the cut points cannot break up the pairs during compaction, all because of it.

Also note the usage of role: the tool result is a separate role="tool" message, the content is plain text (mostly stringified JSON), not assistant. This leads to a very hidden pit in Chapter 6.

Why the loop checks tool_calls instead of finish_reason

The response contains sibling fields finish_reason and message. Typically, finish_reason is "tool_calls" when the model requests tools and "stop" when it finishes speaking. That makes it tempting to use this metadata as the loop condition.

The reason is that the nature of these two fields is completely different:

  • finish_reason is metadata of the service provider: it only describes "how the generation stopped" and is not part of the conversation itself. The values ​​​​of different manufacturers and different compatible endpoints are not completely consistent, and there are differences in actual measurements.
  • And message.tool_calls is a fact written into history by yourself: whether the model has given a tool call or not, just check whether the array is there and whether it is empty. It will always be reliable.

So the criterion in this chapter is "whether there is a non-empty tool_calls in the assistant message" instead of looking at finish_reason. Use facts, not metadata - This is an engineering principle that can be extended to many places.

Why growing history needs compaction

Note that messages in the request body is complete history, not this sentence. Because the model is stateless, you won’t know what you talked about before if you don’t send it.

So there is an account to be settled: assuming that 1 message is generated in each turn, and N messages are sent in the Nth turn. The cumulative amount sent after N turns is 1+2+...+N ≈ N²/2. The cost increases quadratically as conversation length increases.

This is the fundamental reason for the existence of compaction in Chapter 6 - it is not the icing on the cake, but if it is not compressed, the context window will be hit after chatting for a long time, and the API will directly report an error.

Design trade-offs

  • The loop has only one termination condition: there is no tool_calls array in this turn of responses. Don't look at finish_reason - it is the metadata of the service provider, and the naming is not uniform; and "Whether there is tool_calls in the assistant message" is a fact constructed by you, and it is always reliable.
  • Models are stateless. It doesn't remember what it said in the previous turn, so it has to resend the complete history in each turn. This is the root cause of all agent cost structures and why Chapter 6 compresses history.
  • Assistant messages should be saved as is. In addition to content, it also has an array of tool_calls. The next turn depends on the id inside to match the result of role="tool". Saving only text will cause the next turn of requests to fail.

Chapter 2

Tools

Give the agent tools
Goal Represent tools as a name-to-function table. Adding a tool should change its declaration and implementation without changing the loop.

The problem

  • If you use if/elif in a loop to determine the tool name, each time you add a tool, the core code must be modified - the more the core code is modified, the easier it is to change.
  • If the tool fails to execute (the file does not exist, the command times out) and an exception is thrown directly, the entire agent will collapse and the user will only see a stack.

How it works

In the loop in Chapter 1, the execution tool section probably looks like this:

if name == "bash":     result = run_bash(inp)
elif name == "read":   result = read_file(inp)
elif name == "write":  result = write_file(inp)
else:                   result = "unknown tool"

This can run. But it has two problems, both of which worsen as the project gets larger.

Problem 1: The loop depends on every tool implementation

Every time you add a tool, you need to change the main loop. The main loop is the file that should be least touched in the entire project - it carries the functions of all subsequent chapters (interruption, compaction, persistence), and if you touch it once, you must re-verify all behaviors.

The solution is the classic table driver: save "Name → Implementation" as a dictionary, and write only one line in the loop: submit(name, input). Adding tools = changing the table, not the logic. Here, tool calls are separated from specific implementations.

Problem 2: Tool failure will crash the agent

File does not exist, command timeout, path out of bounds - these are normal in the agent scenario, not abnormal situations. They can happen at any time because the caller is a fallible model.

If an exception is thrown directly, the entire agent will die and the user will only see a stack. And if the error message is returned to the model as a tool result, it will understand it and change its approach - for example, if it sees "the file does not exist", it will list what is in the directory.

Here is a counter-intuitive but important judgment: The responsibility for error handling is transferred. In traditional programs, errors are handled by the caller; in agents, errors are input to the model. So the tool always returns a string and never throws an exception.

Tool declarations and implementations are separate

The tools parameter of the API requires each tool to provide: name, description, and a JSON Schema description parameter. This statement will be serialized into the request body as it is, and the model relies entirely on it to determine "how should I fill in the parameters".

So there must be two tables in your code:

  • TOOLS - a statement for the model to see. If it is written vaguely, the model will fill in the wrong parameters.
  • HANDLERS - Implementation dictionary for yourself.

Both tables must have the same name. If the name doesn't match, the model will see a tool that is "declared to exist, but must fail when called" - this kind of bug is very hidden, because the model will not say "this tool is not implemented", it will only try again and again.

Why file tools use Python instead of the shell

A natural idea is: to read a file, execute cat xxx, and to write a file, execute echo ... > xxx. Don't do this for three reasons:

  • Quotation mark escaping: If there are spaces or Chinese brackets in the file name, the spelled out command will be broken; if there are quotation marks in the content, it will be even more disastrous.
  • glob expansion: cat *.py will be expanded into a bunch of files by the shell, and the original intention of the model may be a file called *.py.
  • Unable to locate error: The shell only gives you a return code, and you don’t know whether the file does not exist or the permissions are insufficient. If you directly enter open(), OSError will clearly tell you the reason.

A path is a path and content is content. The shell is only reserved for scenarios where you really need to run commands (calling git, running tests).

Keeping file paths inside the working directory

The model may give ../../etc/passwd, or C:\Windows\System32\.... It's not malicious, it's just guessing. But your tool can't really read it.

The solution is to resolve the path into an absolute path and then confirm that it falls within the subtree of the working directory. The key is to use os.path.realpath instead of abspath - the former will expand the symbolic link. Otherwise a soft link pointing to the outside can bypass the check.

Design trade-offs

  • Two tables with different responsibilities: TOOLS is a statement (name, description, parameter schema) for model; HANDLERS is an implementation table for self. The two must have the same name, otherwise the model will see a tool that "exists but cannot be called".
  • Uniform signature (input: dict) -> str so that all tools fit into the same table.
  • Errors are also tool results. If the file cannot be read, "Error: ..." is returned to the model, allowing it to think of other solutions - this is much more useful than crashing the program.
  • Do not use shell for file operations. Just use open() to read the file, do not splice cat xxx: there is no quotation mark escaping problem, no glob expansion, the path is the path.

Chapter 3

Mutation Queue

Coordinate concurrent writes
Goal Execute tools concurrently while keeping each same-file read–modify–write operation inside one critical section.

The problem

  • Concurrency comes first, then queues are needed. This order is very important. There will be no conflicts at all when executed serially.
  • After concurrency, if two edits modify the same file, the updates will be lost:
edit#1: Read "A" ────────────┐
edit#2: Reads "A" ─────┼── Both reads A
edit#1: Write "A1" ─────┘
edit#2: writing "A2" ← overwrites edit#1

How it works

The tools in the first two chapters are serial executed: if the model reads 5 files in one turn, it has to wait for 5 disk IOs. Changing to concurrency is natural—but once you change it, something goes wrong.

Lost updates from concurrent writes

Suppose the model issues two edits in one turn, both modifying the same file:

edit#1: Read "A" ──────────────┐
edit#2: Read "A" ───────┼── Both read A
edit#1: Write "A1" ──────┘
edit#2: writing "A2" ← overwrites edit#1 and its changes disappear

This is not as simple as "whoever writes last wins" - edit#1's changes were completely lost, and no errors were reported. The model thought that both places had been changed, but in fact only one had been changed. This type of bug is called "lost update" and is the most classic problem in concurrent programming.

Note that the root cause is "read-modify-write" and is not atomic. Edit is not a one-time write, but a three-step process of "reading in → calculating new content → writing back". The two edits are executed in an interleaved manner, and the second step is calculated based on expired content.

Why concurrency needs coordinated writes

This order can easily be reversed. There is no conflict at all when executing serially, and this level of coordination is usually not needed when there is no concurrency; the same implementation here already includes a queue, and Chapter 3 focuses on its role.

If you write the queue first and then concurrency, you will get a piece of code that "seems to be protecting something, but in fact there is no concurrency, so you can never detect the problem" - that is a very bad state: you don't know whether it is correct or not.

One lock per path

The easiest way is to add a global lock and queue all disk writes. It can solve the problem, but it also erases the benefits of concurrency - changing a.py and changing b.py are obviously unrelated to each other, but they have to wait for each other.

The correct approach is to bucket by file path:

  • The same file → shares a lock → serial.
  • Different files → each use its own lock → still parallel.

The implementation is a dictionary {path: lock}. When using it, take a handful of setdefault. The relevant implementation is concentrated in FileMutationQueue, but it has three places where it is easy to make mistakes. The following "Implementation Guide" explains each one.

The lock registry has its own race condition

After bucketing by path, there is a more hidden problem: The action of "getting the lock" itself must be serialized. Look at the two lines of code lock = locks.get(key), if lock is None: locks[key] = Lock() - there is a gap in the middle:

Thread A: get(key) → None ──────┐
Thread B: get(key) → None ──┼── Both found "no lock yet"
Thread A: Create lock A and store it in ────────┘
Thread B: Create lock B and save it ← overwrite lock A
Result: Two threads each take a different lock to modify the same file

This is why there are two locks in the module: _registry to protect the dictionary itself, and _locks[key] to protect a certain file. The lock that protects the "lock" and the lock itself are two different things - without the former, the queue does not exist.

These races can be intermittent and appear only under particular timing. Reason about the complete critical section instead of relying on one successful run.

By the way: the corresponding file-mutation-queue.ts in the real project pi only has 61 lines. This kind of "few but critical" concurrency primitives are short in length but have a reason for each line, and are worth reading line by line.

Design trade-offs

  • Bucket by path: The same file is serialized, but different files are still parallel. If only one global queue is used, the writing of unrelated files will also be strung together, which will slow down the process in vain.
  • Key normalization using realpath: Otherwise, ./a.txt, a.txt, and symbolic links will be treated as three different keys, and a lock will be built for each, and the queue will be useless.
  • The step of acquiring the lock itself must also be serialized: Otherwise, two concurrent calls may find that "this lock has not been established yet" at the same time, so each builds one, which means there is no queue.

Chapter 4

Interruption and Steering

Interrupt or redirect a running turn
Goal Allow Ctrl+C to interrupt a turn and let new input steer the next model request while the worker is running.

The problem

  • A turn can take tens of seconds. Keep the main thread available to read new instructions and signal interruption while the worker runs.
  • The interruption itself has a hidden pitfall: if you interrupt the model just after saying "I want to call the tool", an assistant message with only tool_calls and no corresponding role="tool" message will be left in the history - The next request will be directly rejected by the API.

How it works

A turn can take tens of seconds while the model and tools run. If the main thread waits for the entire turn, it cannot read new instructions. Running the agent in a worker thread leaves the main thread available for interruption and steering.

To solve this, you need two different things: Interrupt (I don’t want you to continue) and Turn (I want you to change direction). They look like the same thing, but the mechanics are completely different, hence the two classes.

Why interruption uses an exception

Interruptions may occur deeply: in a utility function that is waiting for an HTTP response at urlopen, waiting for a child process to end, or recursively.

If propagated by return value, the signature of each function must become -> tuple[result, aborted], and each layer must be checked and passed up. This will pollute the code beyond sight, and as long as one layer is missed, the interrupt will fail.

Anomalies are designed to "jump out directly across many levels". Therefore, exceptions are used for interruption: caught at the outermost layer and thrown at the checkpoint.

The cost is that exceptions will skip the normal cleanup logic, so the location of the checkpoint must be carefully selected - it cannot be left in an intermediate state such as "the memory has been changed and the disk has not been written yet."

Why Signal uses threading.Event

In Chapter 4, you must also put the agent in a background thread to run (the main thread can continue to read your input). So the interrupt flag becomes a mutable state shared across threads.

A plain self.flag = True is dangerous here: Python has the GIL, and simple assignments generally won't read torn values, but there are no guarantees about memory visibility and instruction reordering. threading.Event has a lock inside, which is standard practice and also expresses the intention of "this is a synchronization point".

Why steering uses a queue

You may type two or three sentences in a row while the agent is running. If stored in a single variable, the latter sentence will overwrite the previous sentence and the previous sentence will be lost. So use queue.

What’s more critical is the timing of taking away: the request has already been sent, and your sentence cannot be inserted into the current turn. You can only wait until the next turn begins to be inserted into history. So the queue must be cleared once at the beginning of each turn of the loop.

The action of "clearing" must be atomic: if len() is judged first and then pop is passed one by one, and the main thread pushes another one in the middle, it may be missed or repeated. Therefore, we need to use the method of "taking it all at once and replacing it with an empty list" instead of popping in a loop.

Interrupted calls still need tool results

Here you need to pay attention to the pairing of tool calls and results, which can be checked with tests.

Consider this sequence: the model requests the read tool, the loop records the assistant message unchanged, and then you press Ctrl+C before a corresponding result is recorded.

Historically it is now:
  assistant {tool_calls: [{id: "call_A", ...}]} ← Saved
  (There is no corresponding role="tool" message) ← The tool did not run because it was interrupted.

Next request → API reject:
  Assistant message with tool_calls must be followed
  by tool messages for each tool_call_id

The naive way to write it is to write break directly at the interrupt check point. But then the orphan tool_call will be left in history - the next request will be completely rejected by the API, and the error message will not point to the real reason at all (the user will think it is a problem with the model or network).

Correct approach: When interrupted, add a role="tool" message to each unexecuted call. Use tool_call_id for the content and "Error: aborted" for the text, and then exit. In this way history is always legitimate.

The important invariant is the same as in Chapter 1: every recorded tool call needs a matching result. Adding interruption must preserve that pairing even when normal execution stops.

Design trade-offs

  • Use exceptions for interruptions, not return values. Interruptions may occur in deep places (while sending HTTP, waiting for tools), and returning layer by layer will contaminate all function signatures; if an exception is thrown, any checkpoint can jump out immediately.
  • Signal uses threading.Event because the agent runs in a child thread and requires thread-safe cross-thread visibility.
  • Direction queue. The request has been sent out, and your sentence cannot be inserted into the current turn. It can only be saved and inserted into history before the next turn begins. Use a queue instead of a single variable because you might type two sentences in a row.
  • Complete the role="tool" message after interruption. Here you need to ensure that tool calls and results are completely matched.

Chapter 5

Session Persistence

Resume after closing the terminal
Goal Save conversation history to disk so --continue can restore the latest session.

The problem

  • As soon as you close the previous chapters, the dialogue disappears. The context is the most expensive thing of the agent. Throwing it away is equivalent to wasting all the tokens spent before.

How it works

The agents in the first four chapters are forgotten as soon as they pass. The context is precisely the most expensive thing of the agent - it contains the tokens you spent, the files the agent read, and the decisions it made. Throwing it away is a waste of all your money and time.

Why sessions use JSONL

The most intuitive approach is to serialize the entire messages list into a .json file. But every time you append a message, you have to: read the entire file → parse → push → re-serialize → overwrite the entire file.

After changing to JSONL (one JSON per line), the append is just f.write(line + "\n"). Three reasons, in order of importance:

  • Append is cheap: one line per line, O(1) instead of O(file size). When talking about hundreds of turns, the difference is considerable.
  • Crash-safe: Power off when writing line 7, the first 6 lines are still fully parsable. If the entire JSON file is damaged, not a single byte can be read.
  • Tolerant of local damage: If a single row is broken, just skip it without affecting other rows. Real world log files always have half a line in them.

This idea has a name called Event log (event log): only appending, not modifying, the current status is calculated from the replay log. The WAL of the database and the commit history of Git are all the same routine.

Writing a temporary file before replacing history

Appending cannot express every history update. Chapter 6 replaces older messages with one summary, so the session needs a method that rewrites the complete history.

If you directly open the original file and overwrite it, a crash in the middle of writing will directly destroy the entire session. So write xxx.jsonl.tmp first, and then os.replace(tmp, path) after writing.

os.replace is atomic on both Windows and POSIX: either you see the old file or you see the new file, there is no intermediate state. This is a standard way to ensure that data is not damaged in the event of a crash.

Understanding append and persist

Persistence involves two distinct actions: adding a message to the in-memory history and writing its JSONL record to disk. The loop owns the first action; the session hook owns the second. Connecting the wrong method performs the in-memory append twice.

First look at the calling timing of the hook. It is in the _append indirection layer in the loop, with four lines in total:

def _append(messages, msg, on_append):
    messages.append(msg) ← ① The loop itself has put the messages into memory
    if on_append: on_append(msg) ← ② The hook is just a "notification": I have finished changing the memory

The key is ②: when the hook is called, the message is already in memory. So the only thing the hook should do is "write it to the disk" - this is exactly the semantics of persist (only writes to the disk, does not touch the memory). If it is connected to append_message (its semantics is "add an item": both memory + disk are moved), the same action will be done twice:

Loop: messages.append(msg) ← Loop plus the first pass
       → on_append(msg)
       → session.append_message(msg)
         → self.messages.append(msg) ← session added a second time (repeat!)
           self._write_line(msg) ← Only one line is written to the disk

Follow one turn containing a user message, an assistant tool call, and a tool result. When the result has been recorded, the difference between the correct and incorrect hooks is visible below:

 memory disk
user 1 item 1 line (CLI uses session.append, the same as the starting point)
assistant 2 items ← repeated 1 line
tool 2 items ← duplicated 1 line
               ───── ─────
               5 items 3 lines ← From here on the two sides do not match up

Notice which side is wrong: the three records on disk are correct, but memory contains duplicates. The next model request sends the duplicated assistant call and tool result. A strict endpoint may reject their ordering, while a permissive endpoint receives polluted context. Using persist keeps three in-memory messages aligned with three disk records.

Omitting on_append causes the opposite problem: memory contains the whole turn, but disk contains only the user message written by the CLI. Restoring with --continue then loses the assistant and tool messages. Both failures come from an unclear division of responsibilities.

Keep in mind the division of labor among the three methods. If you choose the wrong step, you will fall into the trap above:

  • session.append(role, content) - "I want to add a new one": Memory + disk both move. Used by the CLI when storing user input into the session.
  • session.append_message(msg) - Same as above, except that the complete dict is collected (used when restoring history from disk). Cannot be used as a hook: This is stated in its docstring.
  • session.persist(msg) - "This item is already in the memory, I am only responsible for writing to the disk": Only touch the disk. This is the only way to use hooks.

The root cause is: Both objects think they should change the memory. The solution is to write down the responsibilities into a contract - The loop is responsible for modifying the memory, and the session is only responsible for placing disks. No one will repeat the work of the other. What falls on the CLI is the line on_append=self.session.persist.

This mistake can quietly corrupt history without an immediate error. The useful invariant is simple: after a completed turn, the in-memory messages and the JSONL records should describe the same history.

Preserving Python list identity

There is a similar trap. replace_messages To replace the history as a whole, the intuitive way to write it is self.messages = messages. It's also wrong.

Because both agent_loop and CLI hold the original list object. You let self.messages point to a new list, and the old list is still held by them - the subsequent append will be written into a list that no one has read, and the memory and disk will be permanently decoupled.

The correct way to write it is self.messages[:] = messages - the slice assignment is modified in place, and all holders can see the new content. This difference is very common in Python and is worth remembering separately: = changes the object, [:]= changes the content.

Design trade-offs

  • Use JSONL (one message per line) instead of a JSON array for three reasons: ① It is cheaper to append, just append directly; ② It is crash-safe, and the first 6 lines can still be parsed when the power is off when writing the 7th line; ③ If a single line is broken, it will not affect the whole.
  • This is the idea of event log: only append, not modify, the current status is calculated from the replay log.
  • Two entrances with clear responsibilities: append is "add a message", replace_messages is "overall rewriting" (used for compaction in Chapter 6).

Chapter 6

Context Compaction

Make room in long conversations
Goal As estimated usage approaches the context limit, replace older history with a summary while retaining recent complete turns.

The problem

  • Every turn, the entire history must be sent to the model, and the history only increases - sooner or later the context window will burst, and the API will directly report an error. Even if it doesn't explode, the longer it is, the more expensive and slower it is.
  • Compaction itself has an easy pitfall: if the cut point falls in the middle of a turn, orphan role="tool" messages will be left in the second half, which will also cause the request to be rejected.

How it works

Chapter 1 settled the account: history can only increase but not decrease, and every turn must send out all history. The cost increases by N²/2, and sooner or later it hits the context window of the model, and the API directly reports an error.

The idea of compaction is very straightforward: Give the oldest piece of history to the model, let it write a summary, and then replace the original text with the summary. The complexity is reduced from O(N) to O(1).

Cut history only at a complete turn boundary

Compaction should retain the original words of recent turns (the details are important), and only compress the older ones. Where should the cutting point be? The intuition is to "cut before a certain message in the middle", but this will cause trouble:

If you cut here ↓
  assistant {tool_calls:[{id: "call_A"}]} ← was suppressed
  tool {tool_call_id: "call_A", ...} ← Keep

A message with role="tool" without assistant matching tool_calls appears in the history → API rejection

It’s that agreement restriction from Chapter 1 again. So the cut-off point must fall at the beginning of a turn.

How do you define "turn"? One turn = a user question + all assistant tool calls it triggers + the corresponding role="tool" result + the closing assistant text. The criteria must be looked at carefully - the tool result in OpenAI is independent role="tool" message, not user:

{"role": "user", "content": "Help me change the config"} ← The beginning of a new round ✓
{"role": "assistant", "content": ..., "tool_calls": [{...}]}
{"role": "tool", "tool_call_id": "call_A", ...} ← Independent tool role
{"role": "assistant", "content": "Changed"}

Fortunately, the criterion is still very simple: The new question is role == "user" and content is a plain string. The tool result is role="tool", which naturally will not be regarded as the beginning of a turn - so the criterion role == "user" and isinstance(content, str) is clean and reliable, and the trouble of "distinguishing by content type" no longer exists in the OpenAI protocol.

This is_turn_start is the basis of all compaction logic - no error will be reported if it is written incorrectly, it will only be cut in places that should not be cut, and then explode on the next request.

Choosing how much recent history to keep

After the cut-off point is determined, there is one parameter left to decide: How much to keep. Keeping less will save you a lot, but also leave less of the original text in the context - this section explains how to choose this number.

This tutorial keeps a fixed number of recent turns: compaction_keep_recent_turns, defaulting to three. find_cut_index collects turn-start positions, counts backward to the third-most-recent start, and cuts immediately before it.

turn_starts = [0, 5, 11, 18, 24] # 5 “beginnings of turns” in history
keep=3
cut = turn_starts[len(turn_starts) - keep] = turn_starts[2] = 11

  messages[:11] is used to write summary, messages[11:] is kept as it is.
  Not enough rounds (len(turn_starts) <= keep) → Return None: nothing to stress

Why 3? There is no derivation, it is just a shot - just enough to contain "what I am doing". What is really worth talking about is how to choose this number.

Compacting only enough to fit just below the context limit leaves too little room for the next response and tool output. The next turn can trigger compaction again, repeatedly summarizing summaries and losing detail.

Ask how much useful work can happen before another compaction is needed. Keeping recent complete turns preserves a working area of original messages while creating room for new work.

What unit should be used to measure this work area? All three units have real products in use, and the choices are different:

  • By number of messages (retaining the most recent N messages): The simplest implementation, but the number of messages in a turn is floating - a Q&A with the tool may be 2, or it may be 30, and the actual number of retained messages can vary dozens of times.
  • By number of turns (retain the latest N turns): The retention amount fluctuates with the "size of the turn", but a turn is a unit that users can perceive. They can clearly understand it by reading the log and telling others ("the last three questions are still in the original text"). Take this route for the tutorial version.
  • According to token budget (retain enough recent history of about M tokens): closest to the real constraints, the actual number of turns retained will automatically adapt - if the chat is long-winded, keep a few turns, and if the chat is compact, keep a few more turns; the cost is that tokens must be calculated, and the cut point may fall in the middle of the turn, so additional processing of "cut half turns" is required.

No matter which unit is used, three principles are common:

  • Summarize older messages and preserve recent ones. Current work and fresh tool output need their original detail.
  • The retained unit must be a complete turn: Retaining half a turn is equivalent to creating an unmatched tool message (the constraint in the previous section).
  • The criterion is "whether the work area is enough", not "whether the number of tokens is low enough": The criterion is - when the model continues to work, should it look back to you for original information.

// Accumulate "estimated tokens" from the end forward. Once keepRecentTokens is reached,
// Select the first legal cut point "not less than the current subscript"
/** Find the compaction cut point that keeps approximately the requested recent-token budget. */
export function findCutPoint(
	entries: Entry[],
	startIndex: number,
	endIndex: number,
	keepRecentTokens: number,
): CutPointResult {
	const cutPoints = findValidCutPoints(entries, startIndex, endIndex);

	if (cutPoints.length === 0) {
		return { firstKeptEntryIndex: startIndex, turnStartIndex: -1, isSplitTurn: false };
	}
	let accumulatedTokens = 0;
	let cutIndex = cutPoints[0];

	for (let i = endIndex - 1; i >= startIndex; i--) {
		const entry = entries[i];
		if (entry.type !== "message") continue;
		const messageTokens = estimateTokens(entry.message as AgentMessage);
		accumulatedTokens += messageTokens;
		if (accumulatedTokens >= keepRecentTokens) {
			for (let c = 0; c < cutPoints.length; c++) {
				if (cutPoints[c] >= i) {
					cutIndex = cutPoints[c];
					break;
				}
			}
			break;
		}
	}
	while (cutIndex > startIndex) {
		const prevEntry = entries[cutIndex - 1];
		if (prevEntry.type === "compaction") {
			break;
		}
		if (prevEntry.type === "message") {
			break;
		}
		cutIndex--;
	}
	const cutEntry = entries[cutIndex];
	const isUserMessage = cutEntry.type === "message" && cutEntry.message.role === "user";
	const turnStartIndex = isUserMessage ? -1 : findTurnStartIndex(entries, cutIndex, startIndex);

	return {
		firstKeptEntryIndex: cutIndex,
		turnStartIndex,
		isSplitTurn: !isUserMessage && turnStartIndex !== -1,
	};
}

What the token estimate must include

To know exactly how many tokens there are, you have to calculate them literally using the tokenizer of the corresponding model. That means introducing dependencies, and changing the model requires changing the tokenizer.

This tutorial uses character_count / 3 as a rough estimate for mixed English and Chinese. Leave a reserve: an overestimate compacts early, while an underestimate can exceed the context window and fail the request.

But the "number of characters" only counts content. A place that will be missed: tool_calls of assistant (function name + arguments of each call) and tool_call_id of role="tool" message, they also occupy tokens. Without them, the actual capacity of the history will be underestimated and the compaction timing will be delayed.

So there must be a compaction_reserve_tokens (reservation) in the configuration, and the trigger condition is estimated_tokens > context_window - reserve_tokens, not > context_window.

The prompt determines summary quality

If you just say "summarize this conversation", the model is likely to be written in human-readable prose, leaving out file paths, function names, and reasons for decisions - and those are exactly what will be used in subsequent conversations.

So the summary instruction (SUMMARY_INSTRUCTION) must clearly require:

  • Keep verbatim file paths, function names, variable names, and error messages.
  • Keep decisions made and reasons ("Choose A instead of B because...").
  • Write as a note to your future self, not prose.
  • Don’t be polite, don’t restate the problem, and don’t summarize “what users want.”

The summary instructions directly affect which details the agent retains after compaction. Refine them around exact paths, identifiers, decisions, and unfinished work.

Put the three copies together and the difference can be seen at a glance:

  • The tutorial uses a checklist. It names the information that must survive verbatim but leaves the output format to the model. This keeps the instructions short, at the cost of a less predictable summary format.
  • pi nailed the format: six paragraphs of fixed subtitles (Goal/Constraints & Preferences/Progress/Key Decisions/Next Steps/Critical Context). Each paragraph is also given a line of square brackets written "What to fill in here". At the end, it is emphasized again that the precise path, function name, and error message should be retained. It also has two sentences: Do NOT continue the conversation - to prevent the model from treating the "summary request" as a new task and continue talking.
  • The shortest Codex: The first sentence clearly explains what the task is (CONTEXT CHECKPOINT COMPACTION), and the second paragraph gives four Include. It writes "who is the reader" directly into the first sentence - this is a handoff summary for another LLM who will continue to work.
  • Two things written by all three companies: Make it clear who the summary is for; when naming, you must keep the path, name, decision, and unfinished things. The only difference lies in how strict the format constraints are - the tutorial version relies on lists, pi relies on templates, and the Codex relies on one sentence plus four items.
  • pi also has one more incremental version (UPDATE_SUMMARIZATION_PROMPT): when compressing after the second time, new messages will be merged into the previous version of the summary, instead of compressing the old and new history all over again - its first rule is PRESERVE all existing information from the previous summary. If you want to save tokens, this trick is more effective than any wording optimization.

Two design details

Use role="user" for the summary, not assistant. For the model, "this is background information" is more like a premise explained by the user, rather than what it itself said. Using assistant will make it think that is its own conclusion.

The summary request is an independent one-time request and is not appended to the current conversation. Otherwise, your very act of compressing history is increasing history, which is ridiculous.

Design trade-offs

  • The cut point must fall on the boundary of the "whole turn". One turn = one user question + all assistant (including tool_calls) and role="tool" results it triggers. The criteria are: role == "user" and content is plain string (the tool result has its own role="tool", so there will be no misjudgment; only user + string is considered the beginning of a new turn).
  • Inexact number of tokens, use estimation. The accuracy depends on each word segmenter. Here the number of characters/3 is enough - just leave enough margin to cover the error. It is safer to overestimate than to underestimate.
  • The summary is written by the model and its purpose should be clearly told. Just say "summary" and it might be written in human-readable prose, leaving out file paths and function names - which are really what the rest of the conversation will use.

Chapter 7

System Prompts and Skills

Provide context and project skills
Goal Build the system prompt from general instructions, an environment snapshot, and optional Markdown skill files.

The problem

  • The prompts in the previous chapters are a hard-coded string. It doesn’t know what day it is today, which directory it is in, or what system it is running on.
  • If I want to add some project-specific knowledge to the agent (such as the commit-message conventions specifications of this project), do I have to change the code every time?

How it works

The system prompts in the first six chapters are a hard-coded string. It has two obvious shortcomings: I don’t know where I am (what day is it today, which directory is it in, what system is it in), and cannot be expanded (if I want to add project-specific knowledge, I have to change the code).

This chapter turns it into three pieces spelled out. It seems simple, but all three design points have practical reasons.

Three prompt layers and their order

The large model's attention to different locations in the context is not uniform - strongest at the beginning and end, weakest in the middle (this is the so-called "lost in the middle").

So the arrangement should be determined according to "Importance × Stability":

  • Level 1 · Skeleton: The most critical constraints (how you work, how you speak) are placed at the front. For example, "Read before you write" can significantly reduce the situation where the model changes files based on imagination.
  • Level 3 · Skills: Project-specific knowledge, placed at the end (closer to the end, and more focused).
  • Tier 2 · Environment is sandwiched in the middle. It is pure fact and does not require special attention from the model, so it is most suitable to be placed in the middle.

The base prompt describes general working behavior, such as reading a file before editing it. Project-specific knowledge, such as commit-message conventions, belongs in a skill file.

Local environment snapshots and server prompt caching

Two things need to be distinguished here: saving environment information locally is for less reading and calculation; server-side prompt caching is for reusing the calculated request prefix. The former needs to consider whether the information has expired, and the latter needs to consider whether the prefix is ​​stable.

  • The local cache can be used, but it needs to be updated. Platform information is usually relatively stable; when the directory, date, permissions, etc. change, it needs to be collected again. You cannot simply store all the environment information once and use it all the time, nor do you need to recalculate all fields every time.
  • Server-side cache reuses the same prefix. Changes in the earlier content will affect the longer prefix containing this change; the stable part before the change still has the opportunity to be reused. Actual hits also depend on the model, cache boundaries, length thresholds, retention times, and request routing, and are not guaranteed to be consistent throughout the day.

Basic implementation here: environment_block() reads the directory, platform and date each time it is called, but the CLI only calls build_system_prompt() once when creating App, and reuses self.system_prompt for subsequent requests. Therefore it is actually a startup snapshot and will not be automatically updated after a long session spans days. This simple implementation is retained here.

An optional extension: append environment updates

The open source code of Codex provides a reference method: Treat the environment as a stateful context, save snapshots, compare changes, and then generate update fragments. This not only gives the model newer facts, but also tries to retain what has been sent before.

  • First create an environment snapshot: EnvironmentsState saves information such as the working directory, shell, date, time zone, network and file system permissions; when there is no old snapshot for the first time, compare it to the empty state to generate the required environment context.
  • Subsequent comparison changes: render_diff() generates updates when the directory or other environment fields change compared to the last snapshot; when there are no relevant changes, no environment fragment is generated. Multi-environment scenarios also distinguish between new, changed, and unavailable environments.
  • Environmental facts as independent context: Update renders into a user role fragment with a <environment_context> tag. The user role here is the way the client organizes context, and does not mean that this content is handwritten by the user. The date is also included in the snapshot comparison, and it cannot be generally said that "time does not enter the environmental context at all".

If you continue to expand the agent here, you can use a smaller version: The fixed skeleton and the skills used in the current session form stable instructions; add an environment description when starting a session; check the directory, date and other fields at the beginning of each turn, add updates after the history when there are changes, and clearly refer to the latest environment description. Don't repeatedly rewrite the reminder at the beginning of history just to update the time. After compressing history or restoring a session, also ensure that the model still sees a valid current environment.

For example: keep yesterday's environment description and existing dialogue as they are, add "The current date has been updated to..." after crossing the day; add a new directory description after switching directories. For tasks that require precise time, the clock can be read on demand. This eliminates the need to put timestamps that change every second into fixed instructions.

This organization helps preserve reusable prefixes, but does not guarantee cache hits. Whether there is a real hit or not depends on the cached_tokens returned by the API; the specific fields, billing, and cache settings are subject to the documents of the model used and the service provider. An interface compatible with Chat Completions is used here, and it cannot be assumed that all backends adopt OpenAI's caching rules.

Reference: Codex Environment snapshot and difference update source code (checked for 2026-10-12); OpenAI prompt caching document. This is an optional improvement direction. The following code still uses the basic writing method of assembling prompts at startup.

Why skills are Markdown files

A skill is a Markdown file describing how to perform a class of tasks. For example, git-commit.md can contain the project’s commit-message conventions.

Choosing files instead of code has three benefits:

  • Changing it does not require touching the code, nor does it require revalidation. People who write documentation do not need to know how to write Python.
  • You can prepare it separately by project: If you change a project, you need to change a set of skills/ directories.
  • The content is natural language, which happens to be the form that the model is best at understanding. You don't need to define any schema.

There is another important design principle here: Skills are optional enhancements, and no errors will be reported if they are missing. If the directory does not exist, an empty list will be returned. If a single file cannot be read, it will be skipped. The failure of an enhancement should not block the main process - this is the same idea as Chapter 2 "Tool failure should return error text instead of crashing".

The recurring cost of system prompts

The system prompt is sent with every request. So the longer it is, the greater the fixed overhead is per turn.

Keep skills concise. A rule such as “Write commit messages in Chinese; keep the first line under 50 characters” belongs in a skill file. A copy of the entire project documentation usually does not.

By the way: This also explains why real coding agents put tool descriptions in tool declarations (on demand) and make project documents searchable (the agent reads them by themselves), instead of stuffing them all into system prompts. Each line of system prompts pays for the entire session.

Design trade-offs

  • It is divided into three layers, and the order is important: the skeleton (the most critical constraint) is placed first, and the volatile background information is placed at the back - the model's attention is strongest at the beginning and end.
  • Environment information is collected at the time of call: the date, directory and platform are collected when constructing the prompt; the current CLI is constructed once at startup, and this snapshot is reused for subsequent requests.
  • Skills are skills/*.md files. Changing a markdown does not require touching the code, and it can be prepared separately by project. If the directory does not exist, an empty list will be returned - skills are optional enhancements, and no error will be reported if they are missing.
