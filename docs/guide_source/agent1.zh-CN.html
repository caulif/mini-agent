第 1 章

Agent Loop

把循环跑起来
目标　写一个能自己连着干活的循环：问模型 → 它说要调工具 → 你执行 → 结果塞回去 → 再问一次，直到它不再要工具。

要解决的问题

  • 单次问答的模型没有行动能力 —— 它能告诉你怎么做，但碰不到你的文件。
  • 一旦模型说「我要调工具」，就产生三个新问题：谁执行它？结果怎么回传？什么时候停？

原理

要理解 agent loop，先要接受一个有点反直觉的前提：大模型本身什么也做不了。它是一个纯粹的函数 —— 给它一段文本，它还你一段文本，然后就忘了。它没有记忆、没有手、没有状态。

所以「agent」不是模型的能力，是你写的那个循环。循环的唯一职责是：把模型输出的「我想做某事」翻译成真实动作，再把动作的结果翻译回文本喂给它。智能全在模型里，你的代码只负责搬运和记账。

工具调用到底是什么

模型说「我要调工具」时，它并没有执行任何东西。它只是在输出的 JSON 里多塞了一个 tool_calls 数组，每项形如 {id: "call_01...", function: {name: "read", arguments: "{...}"}}。其中 arguments 是被字符串化的 JSON 参数。这个数组的意思是「如果有一双手，我希望它去读这个文件」—— 执行与否完全取决于你。

理解这一点，整个架构就顺了：循环就是那双手。模型负责想，你负责做，做完再把结果告诉它。

先看清楚：OpenAI 风格的会话长什么样

在动手写循环之前，得先知道一次请求长什么样。整个协议其实只有一个入口：向 {base_url}/chat/completions 发一个 POST。请求体就三大块 ——

POST {base_url}/chat/completions
{
  "model":    "gpt-4o-mini",
  "messages": [                                  ← 整段对话，一个列表
    {"role": "system", "content": "You are a coding agent..."},
    {"role": "user",   "content": "帮我看看 config.py"},
    ...
  ],
  "tools":    [ ...工具声明... ]                  ← 模型能用的"手"
}

messages 是一个列表，每一条形如 {"role": ..., "content": ...}。role 一共就四种，把它们的分工记牢，后面每一章都要用：

  • system：系统提示词，给模型定身份和规则，只放在最前面一条（第 7 章专讲）。
  • user：用户说的话。
  • assistant：模型说的话；它想调工具时，这条消息会多出一个 tool_calls 数组。
  • tool：工具执行的结果，单独一条，靠 tool_call_id 认领它属于哪个调用。

回包也是一个 JSON。真正要紧的只有一条路径：choices[0].message —— 这就是模型这一轮的回复，下一轮你要原样塞回 messages 的就是它：

{
  "choices": [
    {
      "message": { "role": "assistant", "content": null,
                   "tool_calls": [ {"id": ..., "function": {"name": ..., "arguments": ...}} ] },
      "finish_reason": "tool_calls"        ← 同一层的另一个字段
    }
  ]
}

注意 finish_reason 和 message 是同一层的兄弟字段：一个装着模型说的话，一个装着「它为什么会停下来」的说明。这个区别马上就会用到。

背景：想核对字段，去哪看官方文档

上面画的请求和响应不是我编的，是 OpenAI 的 Chat Completions 接口 —— 整个接口只有这一个入口：向 {base_url}/chat/completions 发一个 POST，回来一个 JSON。想核对任何字段的确切含义，看这几页就够：

  • 请求体里每个字段（model / messages / tools / max_tokens …）的定义：api-reference/chat/create
  • 响应对象长什么样（choices → message → content / tool_calls，以及同层的 finish_reason）：api-reference/chat/object
  • 四种角色（system / user / assistant / tool）怎么配合、完整对话示例：api-reference/chat
  • 工具调用这一整套约定（tools 声明、tool_calls 返回、tool_call_id 配对）：guides/function-calling

对照文档你会发现：请求体里这里只用了四个字段 —— model、max_tokens、messages、tools；响应里只读 choices[0].message（文字在 content，工具调用在 tool_calls），其余字段一律忽略。协议很大，agent 需要的是很小一块 —— 流式、多模态、采样参数、logprobs 这些，先当它们不存在。

消息协议的硬约束

OpenAI 风格（chat/completions）对历史结构有强制要求。这条约束是后面好几章所有麻烦的根源，必须一开始就记住：

user      「帮我看看 config.py」
assistant {content: ..., tool_calls: [{id: "call_A", function: {name: read, ...}}]}  ← 只有意图
tool      {tool_call_id: "call_A", content: "..."}                     ← 必须配对
assistant 「这个文件里定义了一个 CONFIG 字典...」                           ← 收工

每个 tool_call 都必须有一条 tool_call_id 相同的 role 为 tool 的消息，一个都不能少、也不能多。后面也会用到这条规则：第 4 章中断时要补配对、第 6 章压缩时切点不能拆散配对，都是因为它。

还要注意 role 的用法：工具结果是单独的 role="tool" 消息，内容是明文（多为字符串化的 JSON），不是 assistant。这一点在第 6 章会导致一个非常隐蔽的坑。

那为什么循环的终止条件不看 finish_reason

上一节看到，finish_reason 和 message 是同一层的兄弟字段，而且它看起来很现成：模型要调工具时它是 "tool_calls"，正常说完话时它是 "stop"。拿它来判断「循环要不要继续」几乎是最自然的写法 —— 但这恰恰是要避免的。

原因在于这两个字段的性质完全不同：

  • finish_reason 是服务商的元数据：它只描述「生成是怎么停下来的」，本身不是对话内容的一部分。不同厂商、不同兼容端点取值并不完全一致，实测有过差异。
  • 而 message.tool_calls 是你亲手写进历史的事实：模型到底有没有给出工具调用，看这个数组在不在、是不是空的就行，永远可靠。

所以本章的判据定为「assistant 消息里有没有非空的 tool_calls」，而不是看 finish_reason。用事实判断，不要用元数据判断 —— 这是个可以推广到很多地方的工程原则。

成本结构：为什么后面一定要压缩

注意请求体里的 messages 是完整历史，不是这一句。因为模型无状态，你不发它就不知道之前聊过什么。

于是有笔账要算：假设每轮产生 1 条消息，第 N 轮要发 N 条。N 轮下来累计发送量是 1+2+...+N ≈ N²/2。对话长度的增长会让成本呈平方级上升。

这就是第 6 章压缩存在的根本原因 —— 不是锦上添花，而是不压缩的话，稍微聊久一点就会撞上上下文窗口，API 直接报错。

设计取舍

  • 循环只有一个终止条件：这一轮响应里没有 tool_calls 数组。不要去看 finish_reason —— 那是服务商的元数据，命名不统一；而「assistant 消息里有没有 tool_calls」是你亲手构造的事实，永远可靠。
  • 模型是无状态的。它不记得上一轮说过什么，所以每一轮都要把完整历史重新发一遍。这是所有 agent 成本结构的总根源，也是第 6 章要压缩历史的原因。
  • assistant 消息要原样存。它除了 content 还有 tool_calls 数组，下一轮要靠里面的 id 去配对 role="tool" 的结果。只存文字会导致下一轮请求失败。

第 2 章

Tools

给 agent 一双手
目标　把工具抽象成「名字 → 函数」的一张表。此后加工具只改一个文件，循环一行都不用动。

要解决的问题

  • 如果在循环里用 if/elif 判断工具名，每加一个工具都要动核心代码 —— 核心代码动得越多，越容易改坏。
  • 工具执行失败（文件不存在、命令超时）如果直接抛异常，整个 agent 就崩了，用户只看到一堆栈。

原理

第 1 章的循环里，执行工具那段大概是这样的：

if name == "bash":     result = run_bash(inp)
elif name == "read":   result = read_file(inp)
elif name == "write":  result = write_file(inp)
else:                   result = "unknown tool"

这能跑。但它有两个问题，而且都会随着项目变大而恶化。

问题一：核心代码被工具列表绑架

每加一个工具就要改一次主循环。而主循环是整个项目最不该动的文件 ——它承载着后面所有章节的功能（中断、压缩、落盘），动它一次就要重新验证全部行为。

解法是经典的表驱动：把「名字 → 实现」存成一张字典，循环只写一行 submit(name, input)。加工具 = 改表，不改逻辑。这里把工具调用与具体实现分开。

问题二：工具失败会把 agent 弄崩

文件不存在、命令超时、路径越界 —— 这些在 agent 场景下都是常态，不是异常情况。它们随时会发生，因为调用方是一个会犯错的模型。

如果直接抛异常，整个 agent 就死了，用户只看到一堆栈。而如果把错误信息当作工具结果返回给模型，它会自己看懂并换个做法 ——比如看到「文件不存在」，它就会去列一下目录里有什么。

这里有个反直觉但很重要的判断：错误处理的责任转移了。传统程序里错误要由调用方处理；在 agent 里，错误是喂给模型的输入。所以工具永远返回字符串，从不抛异常。

发给模型的东西和给自己用的东西，是两份

API 的 tools 参数要求每个工具提供：名字、说明、以及一个 JSON Schema 描述参数。这份声明会被原样序列化进请求体，模型完全靠它来决定「我该怎么填参数」。

所以你的代码里要有两份表：

  • TOOLS —— 给模型看的声明。写得含糊，模型就会填错参数。
  • HANDLERS —— 给自己用的实现字典。

两份表必须同名。名字对不上，模型会看到一个「声明存在、但调用时必然失败」的工具 —— 这种 bug 很隐蔽，因为模型不会说「这个工具没实现」，它只会反复重试。

为什么文件操作不走 shell

一个很自然的想法是：读文件就执行 cat xxx，写文件就 echo ... > xxx。不要这么做，有三个原因：

  • 引号转义：文件名里有空格或中文括号，拼出来的命令就断了；内容里有引号更是灾难。
  • glob 展开：cat *.py 会被 shell 展开成一堆文件，而模型的本意可能就是一个叫 *.py 的文件。
  • 无法定位错误：shell 只给你一个返回码，你不知道是文件不存在还是权限不够。直接 open() 的话，OSError 会明确告诉你原因。

路径就是路径，内容就是内容。shell 只留给真正需要跑命令的场景（调用 git、跑测试）。

路径校验：模型会给出逃逸路径

模型可能给出 ../../etc/passwd，或者 C:\Windows\System32\...。这不是恶意，它只是在猜。但你的工具不能真的去读。

解法是把路径解析成绝对路径，再确认它落在工作目录的子树内。关键是必须用 os.path.realpath 而不是 abspath —— 前者会展开符号链接。否则一个指向外部的软链接就能绕过检查。

设计取舍

  • 两张表，职责不同：TOOLS 是给模型看的声明（名字、说明、参数 schema）；HANDLERS 是给自己用的实现表。两者必须同名，否则模型会看到一个「存在但调不动」的工具。
  • 统一签名 (input: dict) -> str，这样所有工具才能塞进同一张表。
  • 错误也是工具结果。文件读不到就返回 "Error: ..." 给模型，让它自己想别的办法 —— 这比让程序崩溃有用得多。
  • 文件操作不走 shell。读文件就用 open()，不要拼接 cat xxx：没有引号转义问题、没有 glob 展开，路径就是路径。

第 3 章

变更队列

并发写文件不能乱
目标　让一轮里的多个工具并发执行（读 5 个文件不用等 5 次），同时保证同一个文件的「读-改-写」严格串行。

要解决的问题

  • 先有并发，才需要队列，这个顺序很重要。串行执行时根本不会有冲突。
  • 并发之后，两个 edit 改同一个文件就会丢更新：
edit#1: 读到 "A"  ────────────┐
edit#2: 读到 "A"        ─────┼── 两者都读到 A
edit#1: 写入 "A1"       ─────┘
edit#2: 写入 "A2"                  ← 覆盖了 edit#1

原理

前两章的工具是串行执行的：模型一轮里要读 5 个文件，就得等 5 次磁盘 IO。改成并发很自然 —— 但一改就出事。

丢失更新：并发写文件会丢东西

假设模型一轮里发出两个 edit，都改同一个文件：

edit#1: 读 "A"   ──────────────┐
edit#2:     读 "A" ──────┼── 两者都读到 A
edit#1: 写 "A1"  ──────┘
edit#2:     写 "A2"      ← 覆盖了 edit#1，它的改动消失了

这不是「谁后写谁赢」那么简单 —— edit#1 的改动彻底丢了，而且没有任何报错。模型以为两处都改了，实际只改了一处。这类 bug 叫「丢失更新」（lost update），是并发编程里最经典的一类问题。

注意 root cause 是「读-改-写」不是原子的。edit 不是一次写入，而是「读进来 → 算新内容 → 写回去」三步。两个 edit 交错执行，第二步就会基于过期的内容计算。

关键判断：先有并发，才需要队列

这个顺序容易被搞反。串行执行时根本不会有冲突，没有并发时通常不需要这层协调；这里的同一份实现已包含队列，第 3 章集中说明它的作用。

如果你先写队列再写并发，会得到一段「看起来在保护什么、但其实没有并发所以永远测不出问题」的代码 —— 那是很糟的状态：你不知道它到底对不对。

设计：按路径分桶，而不是一条全局锁

最省事的做法是加一把全局锁，所有写盘都排队。它能解决问题，但把并发的好处也一起抹掉了 —— 改 a.py 和改 b.py 明明互不相干，却要互相等待。

正确做法是按文件路径分桶：

  • 同一个文件 → 共用一把锁 → 串行。
  • 不同文件 → 各用各的锁 → 依然并行。

实现就是一个字典 {路径: 锁}，用的时候 setdefault 取一把。相关实现集中在 FileMutationQueue 中，但它有三个容易写错的地方，下面「实现指导」逐一说明。

隐藏的第二层竞态：取锁这个动作本身

按路径分桶之后，还有一个更隐蔽的问题：「拿到那把锁」这个动作本身也要串行。看两行代码 lock = locks.get(key)、if lock is None: locks[key] = Lock() —— 这中间是有缝的：

线程A: get(key) → None  ──────┐
线程B:      get(key) → None ──┼── 两者都发现「还没有锁」
线程A: 建 A锁，存进去 ────────┘
线程B:     建 B锁，存进去    ← 覆盖了 A锁
结果：两个线程各拿一把不同的锁去改同一个文件

这就是为什么模块里有两把锁：一把 _registry 保护那个字典本身，一把 _locks[key] 保护某个文件。保护「锁」的锁，和锁本身，是两件事 —— 漏掉前者，队列等于不存在。

这类 bug 的特点是偶发：平时跑得好好的，压力一大才丢更新。所以它不能靠测试发现，只能靠推理写对。

顺带一提：真实项目 pi 里对应的 file-mutation-queue.ts 也只有 61 行。这类「少而关键」的并发原语，长度短但每行都有理由，值得逐行读懂。

设计取舍

  • 按路径分桶：同一个文件串行，不同文件仍然并行。如果只用一条全局队列，无关文件的写盘也被串起来，白白变慢。
  • key 用 realpath 归一化：否则 ./a.txt、a.txt、符号链接会被当成三个不同的 key，各自建一把锁，队列形同虚设。
  • 取锁这一步本身也要串行：否则两个并发调用可能同时发现「这把锁还没建」，于是各建一把，等于没有队列。

第 4 章

中断与转向

跑起来之后怎么插手
目标　agent 在跑的几十秒里，你既能 Ctrl+C 叫停，也能顺手补一句话改变它的方向。

要解决的问题

  • agent 跑一轮可能要几十秒。如果主线程傻等，你既没法中断，也没法补话。
  • 中断本身有个隐蔽的坑：如果模型刚说完「我要调工具」你就中断，历史里会留下一条只有 tool_calls、没有对应 role="tool" 消息的 assistant 消息 —— 下次请求会被 API 直接拒绝。

原理

agent 跑一轮可能要几十秒（模型思考慢 + 工具执行慢）。如果主线程傻等，你既没法叫停，也没法补话 —— 只能干看着它烧钱。

要解决这个，需要两样互不相同的东西：中断（我不想让你继续了）和转向（我想让你改个方向）。它们看起来像同一件事，但机制完全不同，所以要两个类。

中断：为什么用异常，而不是返回值

中断可能发生在很深的地方：正在 urlopen 等着 HTTP 响应、正在等待一个子进程结束、正在递归的某个工具函数里。

如果用返回值传播，每个函数的签名都要变成 -> tuple[result, aborted]，每一层都要检查并向上传递。这会把代码污染得没法看，而且只要漏掉一层，中断就失效。

异常天生就是为「跨越很多层直接跳出去」设计的。所以中断用异常：在最外层捕获，在检查点抛出。

代价是异常会跳过正常的清理逻辑，所以检查点的位置要慎重选 —— 不能扔在「已经改了内存、还没写磁盘」这种中间状态上。

Signal 为什么用 threading.Event

第 4 章同时要把 agent 放到后台线程里跑（主线程才能继续读你的输入）。于是中断标志就变成了跨线程共享的可变状态。

一个普通的 self.flag = True 在这里是危险的：Python 有 GIL，简单赋值一般不会读到撕裂的值，但内存可见性和指令重排没有任何保证。threading.Event 内部有锁，是标准做法，也表达了「这是个同步点」的意图。

转向：为什么用队列，而不是一个变量

你可能在 agent 跑的时候连打两三句话。用单个变量存的话，后一句会覆盖前一句，前一句就丢了。所以用队列。

更关键的是取走的时机：请求已经发出去了，你这句话没法塞进当前这轮，只能等下一轮开始前插进历史。所以队列必须在循环的每轮开头被清空一次。

而「清空」这个动作必须是原子的：如果先 len() 判断再逐个 pop，中间主线程又 push 了一条，就可能漏掉或重复。所以要用「一次性取走并替换成空列表」的写法，而不是循环 pop。

最隐蔽的坑：孤儿 tool_call

这里需要注意工具调用与结果的配对，可以用测试检查。

时序是这样的：模型回复「我要调 read 工具」→ 循环把这个 assistant 消息原样存进历史（第 1 章的要求）→ 你在这个瞬间按了 Ctrl+C。

历史里现在是：
  assistant {tool_calls: [{id: "call_A", ...}]}   ← 存进去了
  （没有对应的 role="tool" 消息）                 ← 因为中断了，工具没跑

下次请求 → API 拒绝：
  Assistant message with tool_calls must be followed
  by tool messages for each tool_call_id

天真写法是在中断检查处直接 break。但那样历史里就留下了孤儿 tool_call —— 下次请求会被 API 整个拒绝，而且报错信息完全指不到真正的原因（用户会以为是模型或网络的问题）。

正确做法：中断时给每个没执行的调用补一条 role="tool" 消息，内容用 tool_call_id 对上、正文写 "Error: aborted"，然后再退出。这样历史始终是合法的。

这个坑的本质是：第 1 章那条「每个 tool_call 必须有配对」的协议约束，在第 4 章引入中断之后才真正被违反。每加一个新功能，都要回头检查它是否破坏了之前的约束。

设计取舍

  • 中断用异常，不用返回值。中断可能发生在很深的地方（正在发 HTTP、正在等工具），一层层往上 return 会污染所有函数签名；抛异常则任何检查点都能立刻跳出。
  • Signal 用 threading.Event，因为 agent 跑在子线程里，需要线程安全的跨线程可见性。
  • 转向用队列。请求已经发出去了，你这句话没法塞进当前这轮，只能存起来等下一轮开始前插进历史。用队列而不是单个变量，因为你可能连打两句。
  • 中断后要补齐 role="tool" 消息。这里需要保证工具调用和结果完整配对。

第 5 章

会话持久化

关掉还能接着聊
目标　对话落到磁盘上，--continue 能恢复上次那一段。

要解决的问题

  • 前面几章一关掉，对话就没了。上下文是 agent 最贵的东西，丢掉它等于把之前花的 token 全浪费了。

原理

前四章的 agent 一关就忘。而上下文恰恰是 agent 最贵的东西 ——里面有你花掉的 token、agent 读过的文件、它做过的决策。丢掉它等于把之前所有的钱和时间都浪费了。

格式选择：JSONL，而不是一个 JSON 数组

最直觉的做法是把整个 messages 列表序列化成一个 .json 文件。但每追加一条消息，都要：读出整个文件 → 解析 → push → 再序列化 → 整份覆盖写。

改成 JSONL（一行一条 JSON）之后，追加就只是 f.write(line + "\n")。三个理由，按重要性排序：

  • 追加便宜：一行一条，O(1) 而不是 O(文件大小)。聊到几百轮时这个差距很可观。
  • 崩溃安全：写到第 7 行时断电，前 6 行仍然是完整可解析的。整个 JSON 文件损坏的话，一个字节都读不出来。
  • 能容忍局部损坏：单行坏掉跳过它就好，不影响其他行。真实世界的日志文件里总会有半行。

这个思路有个名字叫事件日志（event log）：只追加、不修改，当前状态由重放日志算出来。数据库的 WAL、Git 的 commit 历史 都是同一个套路。

并发写盘：为什么先写临时文件再改名

有一种操作没法用「追加」表达：整体重写。第 6 章的压缩会把前 N 条换成 1 条摘要 —— 这不是追加，是替换。

如果直接打开原文件覆盖写，写到一半崩溃就直接毁掉整个会话。所以要先写 xxx.jsonl.tmp，写完再 os.replace(tmp, path)。

os.replace 在 Windows 和 POSIX 上都是原子的：要么看到旧文件，要么看到新文件，不存在中间状态。这是保证「崩溃时数据不损坏」的标准手法。

最容易写错的地方：append 与 persist 的区别

落盘这件事只有两个动作：改内存（把消息加进对话列表）和写磁盘（往这一行的 JSONL 后面追加）。第 5 章把这两个动作拆给了两个对象 —— 循环改内存，session 写磁盘。钩子 on_append 就是这条契约的接口：一个动作只能有一个负责人，接错方法就会让某个动作被做两遍。

先看清钩子的调用时机。它就在循环里那层 _append 间接里，共四行：

def _append(messages, msg, on_append):
    messages.append(msg)          ← ① 循环自己已经把消息放进内存了
    if on_append: on_append(msg)  ← ② 钩子只是「通知」：我改完内存了

关键在 ②：钩子被调用时，那条消息已经在内存里了。所以钩子唯一该做的事就是「把它写进磁盘」—— 这正是 persist 的语义（只写磁盘，不碰内存）。如果接成 append_message（它的语义是「新增一条」：内存 + 磁盘都动），同一个动作就被做了两遍：

循环:  messages.append(msg)              ← 循环加第一遍
       → on_append(msg)
       → session.append_message(msg)
         → self.messages.append(msg)    ← session 又加第二遍（重复！）
           self._write_line(msg)        ← 磁盘只写了一行

跟着走一轮就看得见后果。假设这一轮是「用户一句 + 模型一次工具调用 + 一条工具结果」，循环跑到工具结果落盘为止：

               内存                       磁盘
user           1 条                       1 行  （CLI 走 session.append，同起点）
assistant      2 条 ← 重复了一份          1 行
tool           2 条 ← 重复了一份          1 行
               ─────                      ─────
               5 条                       3 行  ← 从这里开始两边对不上

注意哪边才是错的：磁盘那 3 行是对的，多出来的是内存。所以它不会在写盘的瞬间炸出来 —— 磁盘并没有少写东西。代价在模型那一侧：下一轮请求会把这段「自己重复自己」的历史发出去，assistant 的 tool_calls 和配对的 tool 消息各出现两次，配对关系被写坏。严格的 API 会直接拒绝（报错大意是「assistant 的 tool_calls 后面必须紧跟配对的 tool 消息」）；宽松一点的照跑，但上下文被污染、白烧 token。换成 persist 就是内存 3 条 = 磁盘 3 行，永远同步。

反方向也接得错：干脆忘了接钩子（on_append 不传，或传了个什么都不做的函数）。这时内存是对的、磁盘只剩 CLI 自己写的那条用户消息（实测：内存 3 条、磁盘 1 行），--continue 回来就只剩你问的那句话。所以「它怎么忘了刚才说的话」这个症状主要来自这一种；而接成 append_message 的直接后果是内存里的历史被写坏。两种错法方向相反，但都会让两边不一致 —— 这就是为什么要靠契约，而不是靠「看起来对」。

三个方法的分工记牢，选错一步就掉进上面的坑：

  • session.append(role, content) —— 「我要新增一条」：内存 + 磁盘都动。CLI 把用户输入存进会话时用它。
  • session.append_message(msg) —— 同上，只是收完整 dict（从磁盘恢复历史时用）。不能当钩子：它的 docstring 里就写明了这句。
  • session.persist(msg) —— 「这条已经在内存里了，我只负责写盘」：只碰磁盘。钩子只能用这个。

根因一句话：两个对象都以为自己该改内存。解法是把职责写死成一条契约 —— 循环负责改内存，session 只负责落盘，谁也不重复对方的活。落到 CLI 上就是那一行 on_append=self.session.persist。

这个错误可能不会立即报错，却会悄悄破坏历史。关键不变量很简单：一轮完成后，内存中的消息与磁盘上的 JSONL 记录应描述同一份历史。

另一个 Python 坑：列表身份

还有一个类似的陷阱。replace_messages 要整体替换历史，直觉写法是 self.messages = messages。也是错的。

因为 agent_loop 和 CLI 都持有原来那个 list 对象。你让 self.messages 指向一个新列表，旧列表仍然被它们拿着 ——之后的 append 会写进一个已经没人看的列表，内存与磁盘从此永久脱钩。

正确写法是 self.messages[:] = messages —— 切片赋值是就地修改，所有持有者都能看到新内容。这个区别在 Python 里非常常见，值得单独记住：= 换对象，[:]= 换内容。

设计取舍

  • 用 JSONL（一行一条消息），不要一个 JSON 数组，三个理由：① 追加便宜，直接 append；② 崩溃安全，写第 7 行时断电前 6 行仍可解析；③ 单行坏掉不影响整体。
  • 这是事件日志思路：只追加、不修改，当前状态由重放日志算出来。
  • 两个入口，职责分明：append 是「新增一条消息」，replace_messages 是「整体重写」（第 6 章压缩要用）。

第 6 章

上下文压缩

历史太长怎么办
目标　当估算的 token 逼近模型窗口时，把最老的一段历史压成一段摘要，用摘要替换原文。

要解决的问题

  • 每一轮都要把全部历史发给模型，而历史只增不减 —— 迟早撑爆上下文窗口，API 直接报错。就算没爆，越长也越贵越慢。
  • 压缩本身有个很容易踩的坑：如果切点落在一轮中间，后半段会留下孤儿 role="tool" 消息，同样导致请求被拒。

原理

第 1 章算过那笔账：历史只增不减，而每轮都要把全部历史发出去。成本按 N²/2 涨，迟早撞上模型的上下文窗口，API 直接报错。

压缩的思路很直接：把最老的一段历史交给模型，让它写成一段摘要，然后用摘要替换原文。复杂度从 O(N) 降到 O(1)。

核心难点：切点必须落在「整轮」的边界上

压缩要保留最近几轮的原话（细节重要），只压老的。那切点该切在哪？直觉是「切在中间某条消息之前」，但这样会出事：

如果你切在这里 ↓
  assistant {tool_calls:[{id: "call_A"}]}   ← 被压掉了
  tool      {tool_call_id: "call_A", ...}   ← 保留下来

历史里就出现了一条没有 assistant 配对 tool_calls 的 role="tool" 消息 → API 拒绝

又是第 1 章那条协议约束。所以切点必须落在一轮的开头。

那「一轮」怎么定义？一轮 = 一条 user 提问 + 它引发的所有 assistant 工具调用 + 对应的 role="tool" 结果 + 收尾的 assistant 文字。而判据要看仔细 —— OpenAI 里工具结果是独立的 role="tool" 消息，不是 user：

{"role": "user",      "content": "帮我改一下 config"}       ← 新一轮开头 ✓
{"role": "assistant", "content": ..., "tool_calls": [{...}]}
{"role": "tool",       "tool_call_id": "call_A", ...}         ← 独立的 tool 角色
{"role": "assistant", "content": "改好了"}

好在判据依然很简单：新提问是 role == "user" 且 content 是纯字符串。工具结果是 role="tool"，天然不会被当成一轮的开头 —— 所以判据 role == "user" and isinstance(content, str) 干净可靠，那层「靠 content 类型区分」的麻烦在 OpenAI 协议里已经不存在了。

这个 is_turn_start 是全部压缩逻辑的基础 —— 写错了不会报错，只会切在不该切的地方，然后在下次请求时炸掉。

保留最近几轮：留几轮、怎么定

切点定下来，还剩一个参数要定：保留多少。留得少省得多，但留在上下文里的原文也少 —— 这一节讲这个数怎么取舍。

教程版的做法最省事：把「保留几轮」写成一个常数 —— 配置里的 compaction_keep_recent_turns（默认 3）。find_cut_index 先把历史里所有「轮的开头」收集起来，从后往前数到第 3 个，切在它前面：

turn_starts = [0, 5, 11, 18, 24]        # 历史里 5 个「轮的开头」
keep = 3
cut = turn_starts[len(turn_starts) - keep] = turn_starts[2] = 11

  messages[:11] 拿去写摘要，messages[11:] 原样保留
  轮数不够（len(turn_starts) <= keep）→ 返回 None：没什么可压的

为什么是 3？ 没有推导，是拍的 —— 够装下「正在做的那件事」就行。真正值得讲的是这个数该按什么取舍。

先看一个容易走偏的直觉：既然目的是别超窗口，那「压到刚好低于阈值」不是最省吗？不是。因为压缩不是一次性动作，而是会反复发生的 —— 只压到贴着阈值，下一轮的回答加工具输出立刻把体积推回去，于是每轮都要再压一次；摘要叠摘要，上下文很快退化成一层层转述。

所以真正要问的不是「压多少才不超窗口」，而是「压完之后还能自由地跑几轮」。这就是「保留最近几轮」的实质：留出一段完整轮的原文当工作区，让接下来几轮都不必立刻再压。

那用什么单位量这段工作区？三种单位都有真实产品在用，取舍不同：

  • 按条数（保留最近 N 条消息）：实现最简单，但一轮的条数是浮动的 —— 一次带工具的问答可能 2 条，也可能 30 条，实际保留量能差几十倍。
  • 按轮数（保留最近 N 轮）：保留量随「轮的大小」波动，但轮是用户能感知的单位，翻日志、讲给别人听都说得清（「最近 3 次提问还在原文里」）。教程版走这条。
  • 按 token 预算（留够约 M 个 token 的最近历史）：最贴近真实约束，实际保留的轮数会自动适应 —— 聊得啰嗦就少留几轮，聊得紧凑就多留几轮；代价是要能算 token，而且切点可能落在轮中间，得额外处理「被切开的半轮」。

不管用哪种单位，三条原则是共同的：

  • 只压老的，不碰新的：正在做的事、刚才那次工具调用的原始输出，都躺在最近几轮里；摘要一定会丢细节，所以这段必须留原文。
  • 保留的单位要是完整的轮：留半轮等于制造一条配不上对的 tool 消息（上一节那条约束）。
  • 判据是「工作区够不够用」，不是「token 数够不够低」：标准是 —— 模型接着干活时，要不要回头向你要原始信息。

/** Find the compaction cut point that keeps approximately the requested recent-token budget. */
export function findCutPoint(
	entries: Entry[],
	startIndex: number,
	endIndex: number,
	keepRecentTokens: number,
): CutPointResult {
	const cutPoints = findValidCutPoints(entries, startIndex, endIndex);

	if (cutPoints.length === 0) {
		return { firstKeptEntryIndex: startIndex, turnStartIndex: -1, isSplitTurn: false };
	}
	let accumulatedTokens = 0;
	let cutIndex = cutPoints[0];

	for (let i = endIndex - 1; i >= startIndex; i--) {
		const entry = entries[i];
		if (entry.type !== "message") continue;
		const messageTokens = estimateTokens(entry.message as AgentMessage);
		accumulatedTokens += messageTokens;
		if (accumulatedTokens >= keepRecentTokens) {
			for (let c = 0; c < cutPoints.length; c++) {
				if (cutPoints[c] >= i) {
					cutIndex = cutPoints[c];
					break;
				}
			}
			break;
		}
	}
	while (cutIndex > startIndex) {
		const prevEntry = entries[cutIndex - 1];
		if (prevEntry.type === "compaction") {
			break;
		}
		if (prevEntry.type === "message") {
			break;
		}
		cutIndex--;
	}
	const cutEntry = entries[cutIndex];
	const isUserMessage = cutEntry.type === "message" && cutEntry.message.role === "user";
	const turnStartIndex = isUserMessage ? -1 : findTurnStartIndex(entries, cutIndex, startIndex);

	return {
		firstKeptEntryIndex: cutIndex,
		turnStartIndex,
		isSplitTurn: !isUserMessage && turnStartIndex !== -1,
	};
}

token 估算：三条都要数到

要精确知道有多少 token，得用对应模型的 tokenizer 逐字计算。那意味着引入依赖、而且换模型就要换 tokenizer。

这里用 字符数 / 3 就够了 —— 对中英文混排是个粗糙但可用的近似。关键是要留足余量：估多了顶多提前压一次（浪费一点钱），估少了就会真的超窗口然后请求失败。

但「字符数」只算了 content。一个会漏算的地方：assistant 的 tool_calls（每个调用的函数名 + arguments）以及 role="tool" 消息的 tool_call_id，它们同样要占 token。漏了它们，history 的实际容量会被低估，压缩时机就会被推迟。

所以配置里要有一个 compaction_reserve_tokens（预留量），触发条件是 估算值 > 上限 - 预留量，而不是 > 上限。

摘要的质量由提示词决定

如果只说「总结一下这段对话」，模型很可能写成给人看的散文，把文件路径、函数名、决策理由全丢了 —— 而那些恰恰是后续对话真正要用的。

所以摘要指令（SUMMARY_INSTRUCTION）必须明确要求：

  • 逐字保留文件路径、函数名、变量名、错误信息。
  • 保留做过的决定和理由（"选了 A 而不是 B，因为..."）。
  • 写成给未来自己的笔记，不要写成散文。
  • 不要客套话、不要复述问题、不要总结「用户想要什么」。

这段提示词的质量直接决定压缩之后 agent 还记不记得住关键信息。值得反复调整。

两个设计细节

摘要用 role="user"，不用 assistant。对模型来说，「这些是背景信息」更像是一条用户交代的前提，而不是它自己说过的话。用 assistant 会让它以为那是自己的结论。

摘要请求是一次独立的一次性请求，不往当前对话里追加。否则你压缩历史的行为本身又在增长历史，很荒谬。

设计取舍

  • 切点必须落在「整轮」的边界上。一轮 = 一条 user 提问 + 它引发的所有 assistant（含 tool_calls）与 role="tool" 结果。判据是：role == "user" 且 content 是纯字符串（工具结果有自己的 role="tool"，天然不会误判；只有 user + 字符串才算新一轮开头）。
  • 不精确数 token，用估算。精确要按各家分词器算。这里用 字符数/3 就够 —— 只要留够余量兜住误差。估多一点比估少安全。
  • 摘要由模型来写，并且要明确告诉它目的。只说「总结一下」，它可能写成给人看的散文，丢掉文件路径和函数名 —— 而那些恰恰是后续对话真正要用的。

第 7 章

系统提示词与技能

让它知道自己在哪
目标　把写死的系统提示词变成「骨架 + 动态环境 + 外部技能文件」三段拼接。

要解决的问题

  • 前面几章的提示词是一行写死的字符串。它不知道今天是几号、在哪个目录、跑在什么系统上。
  • 想给 agent 加一点项目专属的知识（比如本项目的提交信息规范），难道每次都要改代码？

原理

前六章的系统提示词是一行写死的字符串。它有两个明显不足：不知道自己在哪（今天几号、在哪个目录、什么系统），也没法扩展（想加项目专属知识就得改代码）。

这一章把它变成三段拼出来的东西。看起来简单，但三个设计点都有实际理由。

为什么要分三层，以及顺序为什么有讲究

大模型对上下文不同位置的注意力不是均匀的 ——开头和结尾最强，中间最弱（这就是所谓的「lost in the middle」）。

所以排布要按「重要性 × 稳定性」来定：

  • 第 1 层 · 骨架：最关键的约束（你该怎么干活、怎么说话），放最前面。比如「Read before you write」这一条，能显著减少模型凭想象改文件的情况。
  • 第 3 层 · 技能：项目专属知识，放最后面（靠近结尾，注意力也强）。
  • 第 2 层 · 环境夹在中间。它是纯事实、不需要模型特别关注，放在中间最合适。

骨架要写「风格」，不要写「知识」。「你应该先读再写」是风格，任何项目都成立；「这个项目的提交信息要用中文」是知识，应该做成技能文件。

环境信息：两种「缓存」要分开看

这里要区分两件事：本地保存环境信息，是为了少读、少算；服务端的提示词缓存，是为了复用已经计算过的请求前缀。前者要考虑信息是否过期，后者要考虑前缀是否稳定。

  • 本地缓存可以用，但要有更新时机。平台信息通常比较稳定；目录、日期、权限等发生变化时，需要重新采集。不能简单地把所有环境信息存一次就一直使用，也不必把所有字段每次都重算。
  • 服务端缓存复用相同的前缀。靠前的内容变化，会影响包含这处变化的较长前缀；变化之前的稳定部分仍有机会复用。实际命中还取决于模型、缓存边界、长度门槛、保留时间和请求路由，不能保证一天内一直命中。

这里的基础实现：environment_block() 每次被调用时读取目录、平台和日期，但 CLI 在创建 App 时只调用一次 build_system_prompt()，后续请求复用 self.system_prompt。因此它实际上是一份启动时快照，长会话跨天后不会自动更新。这里保留这份简单实现。

更好的做法：固定指令保持稳定，环境变化作为后续上下文补充

Codex 的公开源码提供了一个可以参考的做法：把环境当成有状态的上下文，保存快照、比较变化，再生成更新片段。这样既能给模型较新的事实，也能尽量保留之前已经发送的内容。

  • 先建立环境快照：EnvironmentsState 保存工作目录、shell、日期、时区、网络和文件系统权限等信息；首次没有旧快照时，按空状态比较，生成需要的环境上下文。
  • 后续比较变化：render_diff() 对照上次快照，目录或其他环境字段变化时生成更新；没有相关变化时，不生成环境片段。多环境场景还会区分新增、变化和不可用的环境。
  • 环境事实作为独立上下文：更新渲染成带 <environment_context> 标签的 user 角色片段。这里的 user 角色是客户端组织上下文的方式，并不表示这段内容是用户手写的。日期也在快照比较中，不能笼统说成“时间完全不进环境上下文”。

如果继续扩展这里的 agent，可以采用一个小一点的版本：固定骨架和当前会话使用的技能组成稳定指令；开始会话时补一份环境说明；每轮开始时检查目录、日期等字段，变化时在历史后面追加更新，并明确以最新环境说明为准。不要为了更新时间，反复改写历史开头那份提示词。压缩历史或恢复会话后，也要确保模型仍能看到有效的当前环境。

例如：昨天的环境说明和已有对话保留原样，跨天后补一条“当前日期已更新为……”；切换目录后补一条新的目录说明。需要精确时间的任务，可以按需读取时钟。这样不必把每秒变化的时间戳放进固定指令。

这种组织方式有利于保留可复用前缀，但不保证缓存命中。真正是否命中，应看 API 返回的 cached_tokens；具体字段和计费、缓存设置以所用模型及服务商的文档为准。这里使用兼容 Chat Completions 的接口，也不能假定所有后端都采用 OpenAI 的缓存规则。

参考：Codex 环境快照与差异更新源码（核对于 2026-10-12）；OpenAI 提示词缓存文档。这是可选的改进方向，下面的代码仍使用启动时组装提示词的基础写法。

技能：为什么是文件，而不是代码

一个「技能」就是一个 markdown 文件，讲清某类任务该怎么做。比如 git-commit.md 里写好本项目的提交信息规范。

选择文件而不是代码，有三个好处：

  • 改它不需要碰代码，也不需要重新验证程序。写文档的人不用会写 Python。
  • 可以按项目分别准备：换一个项目就换一套 skills/ 目录。
  • 内容是自然语言，正好是模型最擅长理解的形式。你不需要定义任何 schema。

这里还有个重要的设计原则：技能是可选增强，缺了不能报错。目录不存在时返回空列表，单个文件读不了就跳过。一个增强功能的失败不应该阻断主流程 ——这和第 2 章「工具失败要返回错误文本而不是崩溃」是同一种思路。

一个容易被忽略的点

系统提示词是每次请求都发的。所以它越长，每一轮的固定开销就越大。

这意味着把整个项目的文档塞进技能文件是个坏主意。技能应该写精炼的规则（「提交信息用中文，第一行不超过 50 字」），而不是背景资料。

顺带一提：这也解释了为什么真实的 coding agent 会把工具说明放在工具声明里（按需）、把项目文档做成可检索的（agent 自己去读），而不是全塞进系统提示词。系统提示词的每一行都在为整个会话付费。

设计取舍

  • 分三层，顺序有讲究：骨架（最关键的约束）放最前，易变的背景信息放后面 —— 模型的注意力在开头和结尾最强。
  • 环境信息按调用时采集：构造提示词时采集日期、目录和平台；当前 CLI 在启动时构造一次，后续请求复用这份快照。
  • 技能就是 skills/*.md 文件。改一个 markdown 不需要碰代码，而且可以按项目分别准备。目录不存在时返回空列表 —— 技能是可选增强，缺了不能报错。
