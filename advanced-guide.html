Chapter 8

Failures and retries

Retry the request, preserve completed work
Goal　Add bounded retries to one model request while preserving completed tool operations, rather than restarting the entire agent task.

The problem

  • A tool has already written report.txt when the next model request returns 503. The request needs recovery; the network error does not undo the file change.
  • An HTTP success can still contain invalid JSON or incomplete tool arguments. The response must be usable before execution continues.

How it works

A normal tool loop contains two distinct actions: the model returns an intention, and the host executes it. They are adjacent in the code, but they cannot share an unrestricted retry policy. A request can be sent again under an explicit policy; a completed file write has already changed external state.

Keep recovery at the layer that failed

Consider changing report.txt and then summarizing the result. The model first returns write, the program updates the file and saves the tool result, and a second request carries that history. If this second request receives 503, sending the same history again does not require another write.

First request → write intention → file changed → tool result saved
                                                     ↓
                                              Second request
                                              503 → wait → retry
                                                     ↓
                                                Final answer

A file write is a side effect: it changes state outside the function. The term does not mean that the operation is harmful. Repeating an append, for example, can create two records. The advanced write tool overwrites files, but that does not make replaying tools a general recovery strategy.

Failures have different meanings

A 401 usually requires correcting credentials, while a 429 may require waiting. A timeout only establishes that the client obtained no usable response. The server might already have processed the request, so no result does not establish no execution.

ObservationCurrent policyReason
429, 502, 503, 504Retry within the attempt budgetExplicit status allowlist
Other HTTP errorsStop and preserve the statusNo assumption that repetition fixes the problem
Timeout or disconnectUnknown outcome; no automatic retryServer processing cannot be confirmed
Invalid or truncated responseReject before the tool loopNo usable intention was received

Attempts, backoff, and total duration differ

max_retries=2 means one initial attempt plus at most two retries: three sends in total. Backoff starts from 0.5 seconds, grows exponentially, and is multiplied by a random factor from 0.5 to 1.0 to reduce synchronized retries. Retry-After is a lower bound: a requested 30-second wait exceeds the local 10-second cap, so the implementation stops rather than sending early.

The cap limits one backoff, not the whole task. Each request has its own timeout. Signal is checked during backoff and after a response arrives; a blocking urllib read still cannot guarantee immediate cancellation.

Design trade-offs

  • Retry only one HTTP operation; leave tools in the outer loop so the call structure limits replay.
  • Use RequestFailure categories and status codes instead of guessing from arbitrary exception strings.
  • Validate a successful HTTP body before returning it; protocol validity and business input validity are separate checks.
  • This policy does not guarantee that the server processes or bills a request once, and it does not recover crashed tools. Global cost budgets and cross-request deadlines are not implemented.

Chapter 9

Execution records and recovery

Distinguish three kinds of missing result
Goal　Record tool phases alongside conversation history so recovery can distinguish unstarted calls, unknown outcomes, and saved results without blindly replaying tools.

The problem

  • write can change report.txt before the process exits without saving a tool message. An intention in chat history cannot prove that the file was untouched.
  • A missing result might mean no execution or merely no durable record. Recovery needs phase evidence.

How it works

A basic Session records what the conversation said. An execution journal also records how far a tool progressed. These grow together during normal operation, but a process exit can leave different gaps.

What intention, start, and result establish

assistant: call_A requests write
started: call_A is about to execute
actual tool operation
result: the return value of call_A
tool: deliver that result to the model

The assistant record contains the full intention; started is persisted before the operation. The process might exit immediately afterward, or it might change the file and exit before result. Both can leave an unknown outcome. started is not a completion marker.

result retains the return value, while the tool message supports the next model request. Keeping them separate allows recovery to complete the message pair without touching the file again. Each record passes through write, flush, and fsync, but the journal and file change remain separate operations.

Three recovery branches

Journal stateEvidenceRecovery
Intention onlyNo recorded execution startAppend a not-executed result; do not replay
started, no resultThe operation may have happenedBlock continuation with an unknown outcome
result, no tool messageThe return value is savedReuse it to complete the pair

Preserving uncertainty adds manual inspection, but avoids guessing that an operation probably did not happen. --acknowledge-unknown allows continuation after the operator has inspected the state. It certifies neither success nor failure and does not replay the old call.

The journal can fail too

Journal writes use write, flush, and fsync without forming a transaction with the target file. Corrupt records cannot be skipped: losing started changes execution interpretation, and losing result discards recovery evidence. A single-writer lock covers restoration and execution; the lock file remaining on disk does not mean a writer is still alive.

Design trade-offs

  • Use a separate Journal format instead of treating a basic Session as an execution log.
  • Tool errors can become result text. Persistence failures must stop execution rather than masquerading as ordinary tool errors.
  • Restore message pairs without replaying tools; uncertain file state requires human inspection.
  • No transactions for arbitrary external actions, exactly-once execution, automatic state inspection, or basic Session migration are provided. Locking targets local filesystems.

Chapter 10

Streaming responses

Preview text early; execute only a complete intention
Goal　Collect streaming fragments into a complete response for the existing loop. Preview text neither triggers tools nor establishes a history commit.

The problem

  • The screen says that a change is coming, but arguments contains only {"path":. An incomplete input cannot reach file tools.
  • Text already displayed after a disconnect may remain visible. Whether that assistant response belongs in committed history is a separate decision.

How it works

A non-streaming request returns a complete message. A streaming request returns deltas, and both text and tool arguments can be fragmented. Displaying a fragment is harmless to files; executing an incomplete intention is not.

A delta is not a tool invocation

arguments fragment 1: {"path":
arguments fragment 2: "report.txt","content":"hello"}
assembled: {"path":"report.txt","content":"hello"}

The first fragment is neither complete JSON nor a complete path. The collector buffers arguments while text_delta can feed the display. Only a fully validated response returns to agent_loop, which then saves the assistant and executes tools.

Bytes, events, deltas, and messages

SSE ends an event with a blank line. Its data lines form a payload whose JSON describes a delta. One readline is therefore not one assistant message. Tool fragments are grouped by index; call IDs later pair intentions with tool results. These identifiers serve different purposes.

The acceptance threshold

The collector requires both an accepted finish_reason and [DONE], contiguous tool indices, valid arguments, and shared response validation. Truncation, filtering, disconnection, invalid arguments, or cancellation produce no committable response. Commit here means accepting a complete message into history, not a filesystem or database transaction.

A failed stream retains the recorded user input and discards the incomplete assistant. Displayed preview cannot prove that a complete message was accepted. Automatic retries might generate different content, so this path does not join a second generation onto the first.

Design trade-offs

  • Return the same response shape as call_llm so the loop does not consume deltas.
  • Keep preview text separate from argument buffers; incomplete intentions do not enter Journal.
  • Implement a single-choice Chat Completions SSE subset without assuming that other APIs share its event protocol.
  • Compatibility with all providers is unverified. Stream resumption, multimodal input, and immediate cross-thread cancellation of blocking reads are not implemented.

Chapter 11

Tool permissions and stopping

The model proposes; the host authorizes
Goal　Give each runner its own root, tool registry, and current write permission. Enforce authorization at execution time rather than relying on model compliance.

The problem

  • Removing write from tool declarations cannot guarantee that a Provider never returns write. The host must still reject unauthorized calls.
  • A path spelled inside the workspace may resolve outside it. A cancellation flag also cannot reverse an existing write.

How it works

A tool has a declaration for the model and a handler in the host. The declaration helps select an action; authorization decides whether that action can happen. Read-only mode must affect both.

Undeclared does not mean impossible to request

Only read is declared
Provider still returns write("report.txt", "hello")
submit sees allow_write=False → PermissionError
report.txt must not appear

The execution entry checks name, authorization, and the argument object. Handlers then check business fields. Structurally valid JSON can still contain an escaping path or an invalid content type.

The workspace belongs to the instance

Shared global cwd lets one session change another session's relative-path meaning. WorkspaceTools holds an absolute root and resolves every path from it without os.chdir. Write permission comes from the current --allow-write, not from a previous journal.

Validate the resolved location

Text prefixes cannot distinguish project from project-other or detect an external symlink or junction. path resolves first, then checks ancestry. Journals, Git metadata, device names, and alternate data streams have additional restrictions.

Cancellation is not rollback

Signal blocks subsequent actions at cooperative checkpoints. A check just before writing reduces the cancellation window but cannot undo an operation already underway. A process exit can still leave Journal with an unknown outcome.

Design trade-offs

  • Keep tool state local to an instance without changing the global registry or cwd.
  • Use serial advanced tools without importing the basic concurrent queue or shell.
  • Treat path checks as guardrails in a trusted local host, not as an OS sandbox for Python plugins.
  • No OS sandbox, authorized shell execution, Windows process-tree termination, or file rollback is provided. Trusted handlers retain host Python privileges.

Chapter 12

Testing and outcome evaluation

Separate a working execution path from model success
Goal　Define artifact criteria before running tasks, drive the real Runtime with offline scripts, and observe control flow, completion state, and files separately.

The problem

  • A successful write does not establish correct content. A final claim of completion cannot replace inspecting the actual file.
  • A scripted Provider preselects actions, so its pass rate is not a real model task-success rate.

How it works

Execution correctness and task effectiveness are different layers. Fault regression checks how code handles given inputs; task evaluation also asks whether the model understands a request, selects useful actions, and produces a valid result.

Start with directly checkable task contracts

TaskScripted actionCriterion
readRead line twoExactly 2: beta\n
write_editWrite, then editFile contains hello world
deny_writeRequest write in read-only modeNo file and a PermissionError result

All three use the real Runtime, Journal, and file tools. Only the intention-producing Provider is scripted, preserving the engineering connections while removing model randomness.

Each attempt needs a clean start

Each attempt creates a temporary directory, input, journal, Signal, and request counter. Otherwise a correct file from one attempt could make a later non-execution pass. Three repetitions of three tasks give nine attempts: repetition checks state and control flow, not model-generation variance.

Interpret report fields separately

Requests count Provider calls; tools count tool_start events, including a rejected write attempt. Duration describes runtime cost. Unmeasured tokens and monetary cost stay null; missing measurement does not mean zero cost.

Final criteria inspect artifacts independently. A 9/9 scripted pass means nine predefined action sequences satisfied their contracts, not 100% model success. Real comparisons also require fixed model conditions, task versions, budgets, and repeated runs.

Design trade-offs

  • Use deterministic Providers to locate engineering regressions without mixing in model changes.
  • Grade actual files and error results rather than trusting completion claims.
  • Keep per-attempt results and nonzero failure exits instead of returning only one aggregate percentage.
  • There is no real-model baseline, cost collection, statistical-significance claim, or general coding benchmark. This small suite covers only the stated execution paths.

Chapter 13

Session composition and extension interfaces

Connect the lifecycle to one loop
Goal　Compose Provider, Journal, tools, and Signal through explicit interfaces, keeping state per session while leaving turns and message pairing in the agent loop.

The problem

  • Components working separately does not establish that the real entry point connects recovery, authorization, and stopping.
  • Shared cwd, registries, or Signal can let one session affect another.

How it works

agent_loop still requests responses, saves assistants, runs tools, and pairs results. Runtime does not create a second loop. It supplies the objects used at these points, tying them to one execution.

Three connection points

InterfaceLoop positionRuntime responsibility
request_fnObtain a complete responseProvider or transport, plus validation
on_appendAppend a messagePersist a Journal event
tool_runnerExecute an intentionstarted, authorization, tool, result

Basic callers retain defaults when these new interfaces are omitted. The advanced entry point supplies its own objects rather than copying the loop to add SSE or journaling.

Which session owns the state

Runtime A → Journal A / root A / Signal A / registry A
Runtime B → Journal B / root B / Signal B / registry B

Stopping or registering a tool in A does not change B. Two runners using one journal are constrained by a single-writer lock. This is instance-state separation, not multi-agent routing or shared-file conflict resolution.

Composition also specifies what is absent

The current entry does not integrate basic Session migration, shell, the concurrent queue, automatic compaction, or dynamic skills. A fixed system message and complete history are current choices. Compaction in particular must reconcile history rewriting with execution evidence; simply enabling an old hook is not complete integration.

Design trade-offs

  • One Runtime owns session objects without changing global cwd.
  • Providers are replaceable, but response validation and tool authorization remain mandatory.
  • Plugins are registered trusted host functions, not model-driven imports or remote code downloads.
  • Session branches, multi-agent collaboration, remote plugins, and complete Provider configuration management are absent. Registration does not establish the trustworthiness of extension code.
