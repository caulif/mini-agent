第 8 章

失败与重试

只重发请求，不重做已经发生的操作
目标　给一次模型请求增加有限重试，同时保留已经完成的工具操作；不把整个 agent 任务从头再跑。

要解决的问题

  • 工具已经把 report.txt 写好了，下一次模型请求却返回503。此时需要重发的是请求，文件修改不会因为网络错误而撤销。
  • HTTP 请求成功也可能收到坏 JSON 或半截工具参数。决定是否继续执行之前，还需要判断响应本身是否可用。

原理

一次正常工具循环里有两种动作：模型返回下一步意图，宿主执行这个意图。两者在代码里相邻，却不能用同一种方式重试。请求可以在约定范围内再次发送；写文件一旦发生，就已经改变了外部状态。

失败的是哪一步，重试就应该留在哪一层

以“修改 report.txt 后概括结果”为例，模型先返回 write，程序写入文件并保存 tool 结果，再发下一次请求。第二次请求遇到503时，历史里已经有写入结果；再次发送这份历史，并不需要回到 write。

第一次请求 → write 意图 → 文件已写入 → 保存 tool 结果
                                           ↓
                                   第二次模型请求
                                   503 → 等待 → 重发
                                           ↓
                                      最终回答

写文件这类改变外部状态的动作叫作副作用。它不是“有害行为”的同义词，只说明重新运行代码可能再次改变现场。如果操作是追加记录，重复执行就可能产生两条记录；当前进阶 write 是覆盖写入，也不能因此把重跑工具当作通用恢复方式。

失败不是一个统一的类别

401通常需要修正凭据，429可能需要等待，网络超时则只说明客户端没有取得可用响应。服务端可能已经处理了超时请求，所以“没有收到结果”不能解释成“没有执行”。

情况当前策略原因
429、502、503、504次数预算内重发明确允许的状态码
其他HTTP错误停止并保留状态码不推断重复发送能修复
超时或断连结果未知，不自动重发无法确认服务端是否处理
坏结构或明确截断拒绝交给工具循环尚未得到可用意图

重试次数、等待和总耗时是三件事

max_retries=2 表示首发加最多两次重试，总计最多3次。退避等待从0.5秒起按指数增加，再乘0.5—1.0的随机量，避免多个客户端同时重发。Retry-After 是服务端要求的等待下限；要求30秒而本地上限10秒时，当前代码停止，不会提前发送。

10秒只是一次退避的上限。每次请求还有自己的超时，因此它不是总任务时限。Signal 能打断退避，也在响应返回后检查；阻塞的 urllib 读取仍不能保证即时取消。

设计取舍

  • 重试函数只包一次HTTP操作；工具执行留在外层循环，结构上缩小重放范围。
  • 用 RequestFailure 的类别与状态码判断，不从任意异常字符串猜测是否重发。
  • 成功读取HTTP正文后仍校验响应；协议有效与业务参数有效分别处理。
  • 当前策略不保证服务端只处理或计费一次，也不提供工具崩溃恢复；全局费用预算与跨请求总时限未实现。

第 9 章

执行记录与恢复

把“没有结果”拆成三种状态
目标　在聊天历史之外记录工具阶段，恢复时区分未开始、结果未知与结果已保存，不盲目重做旧调用。

要解决的问题

  • write 改完 report.txt 后，进程可能在保存 tool 消息之前退出。聊天记录里只有意图，无法证明文件没有被改过。
  • 一条缺失的结果消息既可能表示未执行，也可能只是没有来得及落盘；恢复必须依据执行阶段。

原理

基础 Session 回答“这段对话说过什么”，执行日志还要回答“工具走到了哪一步”。这两份信息在正常运行时一起增长，进程退出时却可能留下不同缺口。

意图、开始与结果各证明什么

assistant：call_A要求write
started：call_A准备执行
实际工具操作
result：call_A的返回值
tool：把call_A的结果交回模型

assistant 保存完整调用意图，started 在操作之前落盘。它只证明准备执行：程序可能写完started就退出，也可能已经写完文件但还没保存result。因此started不是完成标记。

result 保存执行返回值，tool 消息用于下一次模型请求。二者分开，恢复器才能在result已保存时补消息，而不用再执行文件操作。

恢复的三种分支

日志状态已有依据恢复
只有意图没有进入已记录的执行阶段补未执行说明，不重放
started，无result操作可能已经发生结果未知，阻止续跑
result，无tool消息返回值已经保存复用结果补配对

保留未知会增加一次人工核对，但比猜测“应该没执行”更可靠。--acknowledge-unknown 表示操作者允许核对后继续；它不认证旧操作成功或失败，也不会重新执行旧调用。

日志也有自己的失败方式

Journal 每条记录经过write、flush、fsync，但它与实际文件不是同一个事务。日志损坏不能跳过：丢一条started会改变执行判断，丢一条result会抹去恢复依据。单写者锁覆盖恢复和运行，防止两个进程各补一次消息；锁文件存在不代表进程仍在运行。

设计取舍

  • 独立Journal格式，不把基础Session文件自动当作执行日志。
  • 工具错误可以变成结果文本，日志落盘失败必须中止，不能伪装成普通工具错误。
  • 恢复只补历史配对，不自动重放旧工具；文件现场的未知由人工核对。
  • 不提供任意外部动作的事务、恰好一次执行、自动现场核对或旧Session迁移；锁的适用范围为本机文件系统。

第 10 章

流式响应

文字可以先显示，工具必须等完整
目标　把流式片段收集成原循环可以使用的完整响应；预览文字不触发工具，也不等同于历史提交。

要解决的问题

  • 界面显示了“准备修改”，arguments却只收到 {"path":。半截参数不能传给文件工具。
  • 断流后已经显示的文字可能留在屏幕上，但这次assistant是否应进入正式历史，需要单独判定。

原理

非流式请求一次返回完整消息，流式请求则不断返回delta。文字与工具参数都可能被拆开：显示一个片段很容易，执行一个不完整意图却会改变文件。

增量不是一次工具调用

arguments片段1：{"path":
arguments片段2："report.txt","content":"hello"}
拼接结果：{"path":"report.txt","content":"hello"}

第一段既不是完整JSON，也没有完整路径。收集器先缓存参数；文字可以通过text_delta单独发给界面。只有完整响应通过校验后，才返回给agent_loop，由它保存assistant并执行工具。

字节、事件、增量和消息

SSE用空行结束一个事件，data行组成事件负载，负载里的JSON再描述delta。因此一次readline不等于一条assistant消息。多个工具的片段按index聚合，id则留给后续tool结果配对，二者用途不同。

完整消息的门槛

当前收集器要求合法finish_reason与[DONE]均到达，工具索引连续、参数有效，再通过共享响应校验。length、content_filter、断流、坏参数与停止都不返回可提交消息。这里的提交只是“允许进入正式历史”，不是文件或数据库事务。

断流时保留已记录的用户输入，丢弃未完成assistant。已经展示的预览不能回头证明完整消息曾被接受；自动重试可能生成不同内容，当前流式路径因此不拼接第二次生成。

设计取舍

  • 收集器返回与call_llm相同的响应形状，主循环不理解delta。
  • 文本预览与工具参数缓冲分离；未完成意图不写Journal。
  • 只实现单choice Chat Completions SSE子集，不把其他API事件格式视作相同协议。
  • 未验证所有服务商兼容性；不支持流断点续传、多模态或跨线程即时关闭阻塞读取。

第 11 章

工具权限与停止

模型选择动作，宿主决定能否执行
目标　让根目录、工具注册与本次写授权属于运行器实例，在执行入口检查权限，而不依赖模型自律。

要解决的问题

  • 只从tools声明中删除write，不能保证Provider永远不返回write；宿主仍需拒绝未经授权的调用。
  • 路径名称在工作区下，不代表解析后的位置仍在工作区；停止信号也不能撤销已发生的写入。

原理

工具有两份表示：声明发给模型，handler留在宿主。声明帮助模型选择动作，授权则决定真实动作能否发生。默认只读需要同时影响这两个位置。

未声明不等于无法调用

请求只提供read
Provider仍返回write("report.txt", "hello")
submit检查allow_write=False → PermissionError
report.txt不应产生

执行入口检查名称、授权和参数对象，handler再检查具体业务字段。一个结构完整的JSON响应仍可能包含越界路径或错误content类型。

工作目录是实例状态

两个会话如果共享全局cwd，一个切目录可能改变另一个相对路径的含义。WorkspaceTools保存自己的绝对root，每个路径从该root解析，不使用os.chdir。写权限来自本次--allow-write，不从旧日志继承。

检查的是实际路径

字符串前缀无法区分project与project-other，也无法识别指向外部的符号链接或junction。path先resolve，再检查祖先关系；日志目录、Git元数据、设备名和备用数据流有额外限制。

停止不是回滚

Signal在检查点阻止后续动作。写入开始之前的检查能减少停止后继续操作的窗口，但不能撤销已经开始的修改。进程在操作中退出时，Journal仍可能只能保留未知。

设计取舍

  • 实例工具不改变全局注册表或cwd。
  • 当前工具串行，不接 mini agent-1 的并发队列与shell。
  • 路径检查定位于可信本地宿主，不把Python插件注册称作OS沙箱。
  • 没有OS沙箱、shell授权执行、Windows进程树终止或文件回滚；可信handler仍拥有宿主Python权限。

第 12 章

测试与效果评估

把程序走通与模型做对分开
目标　预先定义任务产物判据，让真实Runtime接受离线脚本驱动，分别观察控制流、结束状态和文件结果。

要解决的问题

  • write返回成功不代表内容正确，最终回答“完成”也不能代替读取实际文件。
  • 脚本Provider预先规定了动作，它的通过率不能当作模型自行完成任务的成功率。

原理

运行机制和任务效果是两个层次。故障回归检查给定输入下程序怎样处理；任务评测还涉及模型是否理解要求、选择有效动作，并产出符合标准的结果。

先固定能直接检查的任务契约

任务脚本动作判据
read读取第二行结果精确为2: beta\n
write_edit先写再编辑文件内容为hello world
deny_write只读时仍提出write无文件且返回PermissionError

三个任务经过真实Runtime、Journal和文件工具，只有生成意图的Provider被脚本替换。这样保留工程连接，把模型随机性移出检查范围。

一次尝试需要新的起点

每个attempt创建临时目录、输入、日志、Signal和请求计数器。否则上一轮的正确文件可能让下一轮没有执行也被判通过。三任务各重复三次得到9个attempt，重复检查的是状态与控制流，不是模型生成方差。

报告中的数值各表示什么

请求数来自Provider调用，工具数来自tool_start，所以被拒绝的write也可能计为一次工具尝试。耗时记录运行代价，未采集的token与费用保留null。没有测量不等于零成本。

最终判据独立读取产物。9/9脚本通过只能说明9次预设动作完成了约定控制流，不能报告为“模型成功率100%”。真实比较还需要固定模型、任务版本、预算和多次运行。

设计取舍

  • 用确定性Provider定位工程回归，避免把模型变化混进机制检查。
  • 以实际文件和错误结果评分，不信任最终文字声明。
  • 保留逐次结果及非零失败退出码，不只输出一个汇总百分比。
  • 没有真实模型基线、成本采集、统计显著性结论或通用coding benchmark；小任务集只覆盖指定运行路径。

第 13 章

会话组合与扩展接口

把生命周期接回同一条循环
目标　通过明确接口组合Provider、Journal、工具与Signal，让每个会话有自己的状态，并保留主循环的轮次和消息配对职责。

要解决的问题

  • 组件各自能工作，不代表实际入口已经接入恢复、授权和停止。
  • 两个会话共享cwd、注册表或Signal，会让一个会话的操作影响另一个。

原理

agent_loop仍负责请求、保存assistant、执行工具与配对结果。Runtime不另造一套循环，而是提供这些位置需要调用的对象，让它们属于同一次运行。

三个接线位置

接口循环何时调用Runtime职责
request_fn获取完整响应Provider或传输路径及校验
on_append追加消息保存Journal事件
tool_runner执行工具意图started、授权、工具、result

基础调用方不传新增接口时仍走默认路径。进阶入口显式接入自己的对象，不因为增加SSE或执行日志而复制主循环。

状态属于哪个会话

Runtime A → Journal A / root A / Signal A / registry A
Runtime B → Journal B / root B / Signal B / registry B

A停止或注册工具不改变B。若两个运行器指向同一日志，则由单写者锁阻止并发使用。这是实例状态分离，不包含多agent的任务路由与共享文件冲突处理。

组合也要说明没有接入什么

当前入口没有基础Session迁移、shell、并发队列、自动压缩或动态技能加载。固定system文本与完整历史是当前选择；尤其自动摘要涉及执行证据与消息改写的协调，不能只把旧钩子打开就算完成。

设计取舍

  • 一个Runtime持有一次会话的对象，不改变全局cwd。
  • Provider可以替换，但完整响应检查和后续工具授权不随替换消失。
  • 插件是可信宿主函数注册，不包含模型驱动import或远程代码下载。
  • 没有会话分支、多agent协作、远程插件或完整Provider配置管理；扩展代码的可信性不由注册接口保证。
